# Obol v10.20

This product-hardening build organizes the remaining modeled Tool Builder inventory into coherent functional slices and tightens the handoff so future agents keep working the real Product Build Next queue while updating release history.

## What changed

- Reorganized the live Tools route's remaining Tool Builder inventory from one flat chip wall into functional implementation slices while keeping every real tool selectable.
- Corrected the follow-up Tools taxonomy so modeled inventory appears inside the normal operator Tool Library categories with status badges intact instead of under a fake backlog/meta category.
- Added canonical Tool Library group aliasing for backlog-specific taxonomy IDs so modeled inventory merges into the existing operator sections instead of creating duplicate mobile Tools categories.
- Added the Tool Builder implementation standard: reuse plumbing, preserve tool identity, and require bespoke profiles before any modeled tool earns `implemented builder` status.
- Exposed grouped modeled inventory through `OBOL_TOOL_BUILDER_IMPLEMENTATION_AUDIT_CURRENT.activeBatches()` and `auditSnapshot()` so future agents can burn down coherent tool families instead of random one-offs.
- Published the Tool Builder implementation audit owner as v10.20 so historical regressions can distinguish this inventory-organization build from the earlier implemented-builder audit.
- Added focused Tool Builder regressions covering taxonomy, grouped active batches, classic-tool classification, and the bespoke/reuse implementation standard.
- Slimmed the README back to an entrypoint with canonical linked docs, one Product Build Next block, explicit generated-block ownership, and a hard changelog rule for product-affecting builds.
- Restored the v10.20 changelog entry as a prepend to the existing release history, not a replacement for older headings.
- Added PR-template release-history fields so product-visible work cannot quietly skip `CHANGELOG.md` again.

## Operator-visible surfaces

- `#/tools` now places modeled and implemented tools in the same operator-facing taxonomy instead of rendering the remaining modeled inventory as one giant unstructured chip wall or a second backlog category.
- Tool chips remain clickable/selectable. `modeled` means the builder contract is still pending, not that the tool has no place.

## Proof boundary

This build organizes and exposes the remaining modeled backlog. It does not promote a modeled tool to implemented unless that tool has the full Tool Builder contract: schema-driven minimum viable command or guided handoff generation, real supplied or Evidence-derived prefill, additive controls, executable Evidence ingestion, conservative proof boundaries, cleanup/report guidance, and Next Steps movement or blocking where supported.

## Historical-test compatibility

Older Tool Builder and note-derivation regression suites were adjusted only where they encoded obsolete README delivery shape. They still require the Tool Builder contract, Product Build Next handoff, note-source boundaries, and changelog discipline, but they no longer force the duplicated README Tool Builder queue section back into the entrypoint.

The follow-up correction preserves the public `groupForTool()` taxonomy IDs used by Tool Builder planning tests while mapping those IDs onto the canonical Tool Library section IDs at render time, so stylesheet-equivalence checks do not see duplicate operator categories.
