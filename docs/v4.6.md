# Obol v4.6

Obol v4.6 works the first large implementation target exposed by the v4.5 README: the canonical Orange Cyberdefense 2025.03 **SCCM branch**.

v4.5 established the rule that newly implemented Orange work should arrive as a complete operator loop: a real methodology card, sensible command controls, explicit operator-side metadata, conservative copy/paste Evidence handling, and connection back into Next Steps. v4.6 applies that contract to SCCM beyond reconnaissance.

Obol remains static, browser-local, review-first, and human-run only. It does not execute commands, install tools, coerce systems, relay authentication, dispatch SCCM jobs, or perform cleanup itself. The operator runs commands externally and pastes terminal output into Evidence.

## SCCM methodology expansion

v4.3 reconciled the existing SCCMHunter reconnaissance card. v4.6 adds four separate SCCM workflow owners rather than overloading reconnaissance with every later action.

### SCCM Credential Recovery

`SCCM Credential Recovery` separates credential-recovery work from simple site discovery.

The card covers:

- SCCM policy retrieval using SCCMSecrets
- distribution-point file review using SCCMSecrets
- administrative client-secret recovery using dploot
- Windows-local SharpSCCM client-secret recovery from disk or WMI

The workflow can produce `credential.candidate` and `sccm.credentials`, but only when pasted output explicitly contains paired credential fields. Startup banners, package listings, policy-download messages, or generic DPAPI output do not automatically create credentials.

### SCCM Relay and Site Takeover

`SCCM Relay and Site Takeover` owns the relay/database-control branch.

The card includes:

- ntlmrelayx target-file relay
- ntlmrelayx MSSQL relay
- SCCMHunter MSSQL takeover planning

Meaningful switches are GUI-controlled, including SMB2 support, SOCKS retention, debug output, optional SQL queries, and SCCMHunter stacked-query mode.

A listening relay service is never proof. v4.6 only supports `relay.success` and `sccm.control_path` when pasted output explicitly reports a successful authenticated relay/session.

### SCCM Administrative Execution

`SCCM Administrative Execution` is separated from relay and discovery.

The card includes:

- SharpSCCM administrative execution against a reviewed managed device
- SCCMHunter administrative interaction

The card can establish only `sccm.execution_confirmed` from explicit successful dispatch/completion output. It does not automatically establish `foothold.windows`, `access.admin`, or `access.system`; those require their own evidence.

### SCCM Cleanup and Post-Exploitation Mapping

`SCCM Cleanup and Post-Exploitation Mapping` makes lifecycle work explicit.

The card covers:

- identifying SCCM resources before removal
- removing a known device/resource by exact identifier
- SCCMHound post-exploitation relationship/session mapping

Cleanup proof establishes `sccm.cleanup_recorded`. SCCMHound mapping establishes `sccm.post_map`. Neither fact is treated as administrative-access proof.

## Operator-side metadata

The v4.0 `operatorSurface40` contract remains authoritative.

v4.6 marks the new SCCM implementations explicitly:

- SCCMSecrets, dploot, ntlmrelayx, SCCMHunter: Kali-side
- SharpSCCM, SCCMHound: Windows-side

This lets the existing **Working from** selector continue to guide implementation choice without a competing execution-context system.

## Orange decision-path integration

The new cards are integrated into the existing v4.4 decision-stage model:

- SCCM credential recovery -> **Map authenticated AD**
- SCCM relay/takeover -> **Test control paths**
- SCCM administrative execution -> **Move with proven access**
- SCCM cleanup/post mapping -> **Deepen host control**

The existing Orange decision signal remains advisory only. The new cards must still be applicable under normal Obol prerequisites before they can appear as user actions.

## Per-context SCCM progress

`assets/core-v4.6.js` adds a compact SCCM branch progress model.

The tracked SCCM phases are:

1. Reconnaissance
2. Credential recovery
3. Relay / takeover
4. Administrative execution
5. Cleanup / post mapping

Progress advances only from successful SCCM activity or explicit SCCM facts in the active context. Another target cannot advance the current target's SCCM branch.

`nextStepsOverview34()` now includes a `sccm46` payload containing SCCM progress and the current Orange coverage delta.

## Conservative terminal Evidence

`assets/intake-v4.6.js` adds explicit high-confidence SCCM command intent for:

- `SCCMSecrets.py policies`
- `SCCMSecrets.py files`
- `dploot.py sccm`
- `SharpSCCM.exe local secrets`
- `ntlmrelayx.py` SCCM relay forms
- `sccmhunter.py mssql`
- `SharpSCCM.exe exec`
- `sccmhunter.py admin`
- `SharpSCCM.exe get devices`
- `SharpSCCM.exe remove device`
- `SCCMHound.exe`

The proof rules intentionally stay narrow:

- credential recovery requires explicit paired credential fields;
- relay/takeover requires explicit successful authentication/relay output;
- administrative execution requires explicit successful dispatch/completion output;
- cleanup requires explicit removal confirmation;
- SCCMHound requires explicit mapping/completion output.

Recognized commands with weak output remain `tried` rather than being promoted to success.

## UI

- current SCCM phase
- next SCCM phase
- current canonical Orange coverage numbers
- grounded SCCM recommendations and their run/evidence readiness
- recent successful SCCM branch activity
