# Obol v4.7

Obol v4.7 is the retroactive reporting-contract release.

The v4.6 README added two project-wide requirements that apply both prospectively and retroactively:

- every path, tool, and evidence flow must fit cleanly into Obol reporting;
- all existing functionality should remain useful and intuitive from the user's perspective across UI, UX, Evidence, Next Steps, and Report.

v4.7 applies those requirements to the existing Orange Cyberdefense 2025.03 methodology integration without changing the strict methodology-completion denominator.

## Reporting traceability contract

Every live Orange-mapped methodology card receives a reporting contract derived from its existing decision stage, canonical mappings, Evidence profile, and finding metadata.

A mapped card is classified as either:

- **finding-bearing** when it already has explicit report finding metadata; or
- **path/context** when the maneuver is useful to the engagement story but should not be forced into a vulnerability finding.

This keeps reconnaissance, ticket hygiene, mapping, cleanup, and other non-finding work useful in generated reports without inflating finding counts.

## Runtime model

`assets/core-v4.7.js` adds:

- `C.orangeReportTrace47(state, lanes)`
- `C.orangeReportCoverage47(lanes)`
- `C.orangeReportReadiness47(state, lanes)`

The trace model follows successful operator-recorded activity only. It preserves:

- engagement context;
- Orange decision stage;
- live methodology card;
- canonical Orange section keys;
- Evidence-profile family;
- finding/path role;
- existing proof-readiness state;
- exact historical command/evidence presence.

The model never creates activity, findings, facts, success, or proof.

## Generated report integration

`assets/report-v4.7.js` adds an **Orange Decision Path & Reporting Traceability** section to both standard and OSCP working drafts when successful Orange-mapped activity exists.

The section records:

- time;
- target/context;
- Orange decision stage;
- technique;
- canonical mapping;
- report role;
- Evidence profile;
- proof-readiness state.

A successful mapped activity with no finding metadata still appears as path/context traceability. It does not become a finding merely because it is part of the Orange path.

## Draft reporting gaps

When a successful mapped activity is missing existing Obol proof requirements, the generated draft includes a **Draft Reporting Gaps** section.

This can surface missing:

- command snapshots;
- evidence snapshots;
- artifact provenance;
- explicit network-path records;
- required external proof confirmations.

These are draft-quality gaps only. They are not findings and do not change the activity's recorded success state.

## Report UI

The existing Report page now receives a compact **Path → evidence → report** panel showing:

- proof-ready Orange-mapped successes;
- finding-bearing mapped successes;
- path/context mapped successes;
- mapped successes that still need reporting attention.

Mapped methodology cards also show their report contract, including finding/path role, Evidence family, and canonical mapping count.

No new primary navigation destination is added.

## Coverage semantics

v4.7 is reporting infrastructure. It does not claim new Orange technique implementation.

The live v4.6 baseline therefore remains:

- 48 / 127 fully implemented;
- 45 partial;
- 34 gaps;
- 0 stale;
- 38% fully implemented;
- 73% represented.

## Compatibility

v4.7 is additive and forward-coercing. Existing browser-local workspaces, Evidence, Next Steps, SCCM progress, Orange decision stages, Kali/Windows execution provenance, proof-readiness state, report modes, and sanitized export behavior remain intact.

## Future work

Future methodology builds should treat report usability as part of the definition of done. A newly implemented Orange branch should normally land with:

1. a real methodology owner;
2. usable GUI command controls where switches are meaningful;
3. conservative copy/paste Evidence parsing;
4. Next Steps placement and decision-path semantics;
5. explicit execution-side metadata when known;
6. report finding/path semantics;
7. proof-readiness and regression coverage.

Continue working from the canonical gap queue and the v4.5 run/evidence contract audit, with the remaining SCCM, persistence, trust, Windows low-access, AD CS, relay/coercion, delegation, ACL, and authenticated-enumeration debt still explicit.
