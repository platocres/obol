# Obol v9.12 - Tool Builder Platform

v9.12 completes the recommended Product Build Next package, **Tool Builder Platform**.

The release establishes the reusable schema, generic renderer, complete runnable-tool inventory lock, and permanent builder contract validation needed before Obol begins migrating representative tool-specific builders such as Nmap, NetExec, Hashcat, ffuf, and secretsdump.

## Stable schema

`data/tool-builder-schema.js` is the stable non-versioned Tool Builder schema owner.

A builder definition now has to describe:

- stable builder and tool identity;
- execution context such as Kali, Windows, Linux, remote shell, or any;
- typed fields and labeled controls;
- target/workspace context autofill;
- credential-mode declarations;
- deterministic command tokens for literals, field arguments, toggles, and choices;
- Evidence expectations and an explicit proof boundary;
- manual-outcome behavior separate from proof;
- report activity/proof lineage;
- secret-field metadata where relevant.

The schema rejects duplicate or malformed fields, invalid references, unsupported credential modes, and builder definitions that expose automatic execution hooks.

## Generic renderer and compiler

`assets/tool-builder-current.js` is the stable generic browser owner.

It can:

- apply context autofill and defaults;
- render labeled form controls from schema data;
- render credential-mode guidance;
- compile deterministic shell commands from structured tokens;
- quote operator-provided arguments safely for shell handoff;
- keep generated command output in an `aria-live` preview;
- copy a reviewed command to the clipboard;
- display the Evidence, manual-outcome, and report-proof boundary beside the command.

It does not execute commands. There is no `child_process`, spawn/exec bridge, eval path, backend, account system, telemetry, or automatic-run hook.

The existing v8.8 current bridge lazily loads the Tool Builder schema, inventory, and renderer on card/tool surfaces. This preserves the stable v9 architecture instead of adding `app-v9.12.js`, `core-v9.12.js`, or another release-specific runtime layer.

## Runnable-tool inventory lock

`data/tool-builder-inventory.js` provides explicit dispositions for runnable tool identities and canonical aliases.

The permanent validator derives tool identities from both the current lane/card command corpus and `OBOL_TOOL_REGISTRY`. Every observed identity must resolve to one explicit disposition:

- `implemented`;
- `modeled`;
- `superseded`;
- `rejected`.

New tool/action data therefore cannot silently bypass builder accounting. CI fails until the inventory is updated deliberately with a rationale. Common aliases such as `nxc`, `cme`, `secretsdump`, `GetNPUsers`, `GetUserSPNs`, and `ntlmrelayx` normalize to stable canonical identities.

Representative queue bindings are included where a specific Product Build Next item already exists. The inventory does not falsely claim those builders are implemented yet.

## Permanent contract gate

`tools/validate-tool-builder-platform.js` is the permanent platform validator. It verifies:

- schema initialization and schema-version stability;
- inventory internal validity;
- complete observed runnable-tool coverage;
- queue-item references from inventory records;
- representative-tool inventory coverage;
- a synthetic schema fixture covering autofill, toggles, choices, field arguments, credential metadata, Evidence boundaries, manual outcomes, and report lineage;
- deterministic shell-safe command compilation;
- generic accessible rendering;
- rejection of automatic execution fields;
- absence of browser execution primitives;
- current-bridge loading of the stable Tool Builder owners.

The synthetic fixture is intentional. v9.12 proves the platform before any representative builder is marked implemented, so the generic engine can be regression-tested without pretending Nmap or another real tool has already migrated.

- `tb-schema` - Define Tool Builder schema;
- `tb-renderer` - Build generic Tool Builder renderer;
- `tb-tool-inventory-lock` - Generate complete tool-builder inventory;
- `qa-builder-contract-test` - Tool builder contract tests.

Tool GUI builders advance from **0/18** to **3/18 complete**. Testing / visual QA advances from **2/8** to **3/8 complete**. Overall Product Hardening advances from **20/632** to **24/632 complete** and the queued item count falls from **54** to **50**. The modeled foundation count remains **9**.

The next highest-priority queued item is `tb-nmap`. Product Build Next therefore advances into the representative Tool Builder set rather than expanding the platform release into the first migration.

## Nmap migration boundary

Obol already has substantial bespoke Nmap builder behavior in the historical/current card corpus. The next release should treat that as behavior to preserve, not throw-away UI.

The generic migration must retain at least:

- first-contact, canonical, deep-dive, UDP, vulnerability, AD, and post-foothold scan profiles;
- scan-type, timing, port-selection, script, script-argument, and output controls;
- context-aware service/script suggestions;
- `-oA` Evidence handoff expectations;
- command rewriting/copy behavior;
- existing failure guidance and regression protection.

Only after the generic Nmap implementation proves behavioral equivalence should bespoke rendering ownership be retired.

## Regression suite

The release regression suite is:

```bash
node tests/run-v9.12-tests.js
```

The permanent validator is:

```bash
node tools/validate-tool-builder-platform.js
```

Product Hardening preflight now runs the validator on every future release. The v9.12 historical suite protects the durable platform milestone without freezing mutable future README release labels, active queue totals, or future Product Build Next ordering.

Release merge-readiness requires the exact final head to pass release smoke, Product Hardening preflight, and the complete ready-PR historical regression chain against the final release description.

## Compatibility

Obol remains static, browser-local, human-run, and backend-free. `C.VERSION` remains `8.8.0`.

v9.12 does not change Evidence proof semantics, recommendation ranking, manual-outcome semantics, report lineage, browser-local workspace storage, the v9.9 loading budget, the v9.10 field-note contract, the v9.11 responsive-density contract, or the frozen Orange baseline.
