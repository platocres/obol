# Obol v4.2

Obol v4.2 turns the Orange Cyberdefense 2025.03 Active Directory methodology source into a **canonical local snapshot** that future agents can read directly from the Obol repository for normal coverage accounting.

The purpose is to remove a structural weakness in v4.1: v4.1 could accurately report completion only against the subset of Orange branches that had already been entered into its audit ledger. v4.2 establishes a fixed denominator from the complete methodology text tree instead.

## Canonical source snapshot

The source-of-truth file is:

`data/orange-ad-2025.03.js`

It is pinned to Orange Cyberdefense `ocd-mindmaps` commit:

`6d16ca0d1434875e0617f2f3cfa825fad0bc7d7e`

and Active Directory source-tree SHA:

`51b414fc0c0a1a4414e86986ec5e2b5225a6d698`

The permanent North Star remains unchanged:

`https://orange-cyberdefense.github.io/ocd-mindmaps/img/mindmap_ad_dark_classic_2025.03.excalidraw.svg`

The snapshot intentionally stores a normalized structural inventory rather than copying every upstream command verbatim. It preserves the complete methodology-file inventory, the source blob SHA for each file, every normalized methodology section used by the completion denominator, source links pinned to the exact upstream commit, and current Obol coverage mappings.

## Canonical denominator

The v4.2 snapshot contains **127 canonical methodology sections**.

At the v4.2 baseline:

- **26 implemented**
- **39 partial**
- **62 gaps**
- **0 stale implemented mappings**
- **20% fully implemented**
- **51% represented** when implemented and partial sections are combined

`fully implemented` is intentionally strict. Partial coverage does not inflate the completion percentage.

This means future agents can use `C.mindmapCoverage42(LANES)` to answer how much of the pinned Orange 2025.03 methodology Obol has fully implemented without revisiting the SVG or re-auditing already-normalized source files.

## Runtime integrity checks

`assets/core-v4.2.js` validates the local snapshot and reports:

- methodology source-file count
- support-file count
- canonical section count
- duplicate section keys
- pinned upstream commit
- pinned AD source-tree SHA
- live card mappings
- stale implemented mappings
- implemented / partial / gap totals
- fully implemented percentage
- represented percentage

An implemented section whose mapped Obol card disappears becomes `stale` instead of remaining silently green.

## When future agents should revisit upstream Orange

Ordinary feature builds should read the local manifest first.

A future agent only needs to inspect upstream Orange directly when:

1. refreshing the pinned Orange snapshot to a newer upstream revision;
2. implementing a specific gap and needing the exact source commands/details for that branch;
3. validating that Orange upstream has changed since the pinned commit;
4. resolving a source-hash mismatch or snapshot-integrity problem.

The normal development loop is now:

`pinned Orange manifest → canonical coverage → priority gaps → implementation → coverage update`

rather than repeatedly reopening the visual mindmap just to reconstruct what exists.

## User-visible completion percentage

The completion percentage is now intentionally hard to miss:

- the application header shows an **Orange AD percentage badge** on every route;
- Home shows a dedicated Orange AD coverage card;
- Methodology shows the full canonical ledger, percentage, represented percentage, source commit, source-tree identifier, and section denominator;
- Methodology can filter by status and source file.

The v4.1 tool-choice audit remains available as a separate concern and is not allowed to alter the canonical denominator.

## Coverage semantics

Each canonical section is one of:

- `implemented` — materially complete for the normalized Orange section;
- `partial` — meaningful Obol coverage exists, but the source section contains additional work;
- `gap` — no materially complete Obol workflow is claimed;
- `stale` — an implemented mapping references a methodology card that no longer exists.

The completion percentage is:

`implemented / canonical sections`

The represented percentage is:

`(implemented + partial) / canonical sections`

## v4.1 compatibility

v4.1's tool-review records and audited execution-side metadata remain intact.

v4.2 replaces the smaller v4.1 audit subset as the completion denominator, but does not remove:

- keep / supplement / replace / review tool decisions;
- explicit `operatorSurface40` execution metadata;
- the Kali-versus-Windows Path requirement;
- existing Methodology cards;
- existing evidence, activity, reachability, pivot, lineage, or reporting state.

## Information architecture

No new primary navigation destination is added.

Ownership remains:

- Home — high-level completion visibility;
- Methodology — canonical Orange coverage ledger and source drill-down;
- Next Steps — engagement-specific evidence-ranked work;
- Evidence — review-first state mutation;
- Report — reproducible engagement reporting.

## Future work

Use the canonical gap queue rather than manually reconstructing the Orange map. High-volume debt is now visibly concentrated in SCCM, domain persistence, authenticated historical vulnerabilities, trust abuse, low-hanging AD/service compromise, cracking variants, AD CS depth, relay depth, and Windows low-access branches.

Future methodology work should continue to evaluate whether Orange's listed tools remain the best user-facing choices. Orange is the design North Star, not a requirement to copy every tool choice blindly.
