# Obol v9.22

Obol v9.22 completes the five-item **Credential Material Platform** work package without changing the v8.8 workspace/runtime schema or weakening the human-run command boundary.

## Credential Material model

`data/credential-material.js` is the stable non-versioned owner for first-class credential material. It represents passwords, NTLM and challenge-response material, Kerberos hashes and ticket files, MSCache2, PFX/certificates, SSH keys, cookies, bearer tokens, API keys, and other opaque secret material with explicit type, context, provenance, sensitivity, and lifecycle state.

New material begins as `candidate`. It can become `validated` only when an independent validation action names reviewed Evidence and an explicit access fact. Generated commands, successful cracking output, manual assertions, and selecting a credential for another builder do not independently prove access.

Existing v2.6/v2.7 typed-artifact behavior remains compatible. Legacy secret typed artifacts are migrated into Credential Material when the current owner initializes, and newly saved credential material can continue to project into the historical typed-artifact categories required by existing workflow behavior.

## Hash routing

Common lab hash shapes are recognized with explicit confidence rather than silently guessed. Structured Kerberos AS-REP/TGS, DCC2/MSCache2, NetNTLMv1/v2, bcrypt, raw SHA1, and common file-backed ticket/certificate/key shapes are recognized directly. A bare 32-hex value is intentionally treated as ambiguous: NTLM is suggested with medium confidence while raw MD5 remains visible as an alternate interpretation.

Recognized crackable material can produce minimum Hashcat and John suggestions. These suggestions are copy/planning handoffs only; Obol never starts either tool.

## Cross-tool handoff

`assets/credential-material-current.js` adds a Credential Material panel beside current schema-driven Tool Builders. Operators can save candidate material once, select it later, and populate declared compatible builder fields without retyping the secret. Password and NTLM material can populate compatible authentication builders; crackable hashes can populate cracking builders; ticket, certificate, SSH key, cookie, and token material can populate compatible declared fields when those builders expose them.

This handoff preserves the existing Tool Builder contract: the operator reviews and runs the generated command externally, then returns output to Evidence.

## Redaction and report boundary

Sanitized exports redact secret Credential Material values while preserving non-secret material paths, context, lineage, and validation state. The current report boundary also redacts known saved secrets from generated report text by default. Redaction does not upgrade candidate material into report-ready proof.
