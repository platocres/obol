# Obol v10.02

Product-hardening release v10.02 completes the Post-mining visual density regression pass.

## Summary

This build adds browser proof that the post-notes Path, Card, and Tools cleanup stays visually usable instead of slowly sliding back into walls of cards, raw historical fragments, or hidden primary actions.

The goal is not to redesign the app in this pass. The goal is to make the cleanup provable: Path still shows one clear best next move, Card still puts why-now/action/evidence first, and Tools still puts direct tool selection, implemented builders, accessories, modes, and collapsed legacy examples in the right order.

## What changed

- Added a dedicated Playwright visual-density smoke for Path, Card, and Tools routes.
- Captured visual-density screenshots for Path on desktop and narrow layouts, representative Card routes, Tools home, ffuf, Hashcat, and Ligolo-ng.
- Failed the browser proof on reintroduced matching-card dumps, wrapper panels, internal cleanup/filler copy, hidden primary actions, missing Evidence loops, missing tool accessories, or obvious narrow-layout overflow.
- Closed the Post-mining visual density regression pass through the existing post-notes queue owner without adding another product-hardening browser runtime extension.
- Kept the modeled tool builder implementation backlog as the next concrete Build Next item after visual proof lands.
- Wired the visual-density smoke into the required browser gate so future UI cleanup regressions are caught on the same exact-head check as the normal browser smoke.
- Added focused v10.02 regression coverage for the proof ledger, queue handoff, browser smoke wiring, screenshot targets, and Path/Card/Tools density assertions.

## Compatibility

Obol remains static and browser-local. No backend, account system, telemetry, install prompt, or automatic command execution was added.

This build is intentionally proof-focused. It does not remove useful related card commands, does not hide tool-specific accessories, and does not convert modeled tools into implemented builders. It proves the cleaned-up surfaces are stable before the next build starts filling in the modeled-tool backlog.
