# Obol v4.8

Obol v4.8 is the **domain persistence branch depth and lifecycle** release.

It is built directly from the priorities retained in the merged v4.7 README: expand domain persistence beyond Golden Ticket, ensure new Orange work has usable command controls plus conservative copy/paste Evidence handling, keep Kali/Windows execution context explicit, and make every workflow useful in reporting and cleanup.

Obol remains static, browser-local, review-first, and human-run only. It does not execute persistence techniques, install tooling, modify systems, mint tickets/certificates, or clean up targets. It builds commands, preserves operator-recorded history, interprets pasted output conservatively, and improves Next Steps/reporting from reviewed state.

## Dedicated persistence owners

v4.8 adds dedicated live methodology cards rather than treating Golden Ticket or generic ACL abuse as owners for the full persistence source branch.

### Silver Ticket Persistence

Kali and Windows implementations are represented separately.

The Evidence profile requires an explicitly saved service-ticket artifact before it can establish:

- `persistence.silver_ticket`
- `kerberos.tickets`

Ticket generation does not establish successful service access.

### DSRM Persistence

The workflow separates the configuration action from verification.

The Evidence profile requires a registry query explicitly showing:

`DsrmAdminLogonBehavior REG_DWORD 0x2`

before it can establish `persistence.dsrm`.

A write command or generic success text alone is not enough.

### Golden Certificate Persistence

The card separates CA backup from forged-certificate creation.

- CA backup can establish certificate material only.
- explicit `certipy forge` saved-PFX output can establish `persistence.golden_certificate` plus certificate material.
- later certificate authentication remains a separate activity and proof boundary.

### Credential Subsystem Persistence

Skeleton Key and custom SSP / memssp are grouped as variants of one high-risk credential-subsystem lifecycle card.

The canonical sections remain **partial** because runtime patching behavior, target version, cleanup, and later credential effects vary by environment.

The Evidence profile requires explicit success confirmation. Command startup text is only a tried activity.

### Diamond and Sapphire Tickets

Advanced forged-ticket workflows receive command controls and conservative saved-ticket Evidence parsing, but both canonical sections remain **partial**.

The reasons are deliberate:

- stronger target/version prerequisites;
- exact PAC/ticket behavior varies;
- saved ticket material does not prove service acceptance;
- broader fixtures are still needed before claiming complete canonical coverage.

### DCShadow

DCShadow now has a dedicated post-compromise workflow and Evidence family, but canonical coverage remains **partial** because safe registration, exact attribute mutation, replication, and restoration are environment-specific.

The command keeps object, attribute, and value operator-supplied rather than hiding a destructive default.

### ACL Persistence Lifecycle

v4.8 gives persistence-specific ACL work its own owner:

1. back up the existing DACL;
2. apply the reviewed ACE;
3. preserve explicit modification evidence;
4. restore from the backup during cleanup.

This is distinct from generic ACL privilege escalation. The canonical `acl-persistence` section can therefore move from partial to implemented without claiming that every ACL abuse is persistence.

## Run / Evidence / reporting contracts

Each new card has:

- explicit execution-side metadata;
- a live Orange decision-stage mapping;
- a v4.5 run/evidence contract;
- a v4.8 copy/paste Evidence profile;
- a v4.7 report contract;
- canonical Orange source provenance.

This means new persistence work follows the same operator loop as the rest of current Obol:

`Next Steps → choose implementation → build/copy command → operator runs externally → paste Evidence → review inferred activity/facts → recalculate Next Steps → report/cleanup`

## Conservative proof boundaries

v4.8 intentionally does not infer:

- service acceptance from a saved forged ticket;
- domain admin from ticket creation;
- durable access from a CA backup alone;
- recovered credentials from memssp module load;
- DCShadow success from startup text;
- administrator access from a DACL write;
- cleanup completion unless the operator records cleanup/restore evidence.

## Persistence progress

`assets/core-v4.8.js` adds a context-scoped lifecycle model:

1. Persistence material
2. Forged ticket / certificate
3. Host credential subsystem
4. Directory persistence
5. Cleanup / verification

Successful mapped activity and explicit persistence facts can advance this lifecycle only inside the active host/domain context.

`C.persistenceProgress48(state, context)` exposes the current/next phase and trail.

`C.persistenceQueue48(state, lanes, context)` exposes live applicable persistence recommendations with run/evidence/report readiness.

The payload is added to `nextStepsOverview34()` as `persistence48`.

The Orange v4.4 decision path remains authoritative as the general methodology-stage model. The v4.8 lifecycle is a focused persistence branch, just as v4.6 uses a focused SCCM branch.

## Reporting lifecycle

`assets/report-v4.8.js` adds a **Domain Persistence Lifecycle** section when successful persistence activity exists.

It preserves:

- context;
- technique;
- canonical Orange mapping;
- Evidence family;
- proof-readiness state;
- a technique-specific cleanup/remediation note.

This composes with the v4.7 Orange reporting trace and Draft Reporting Gaps sections.

Persistence artifacts are therefore not merely commands in Methodology: they remain linked through activity, Evidence, proof readiness, report output, and cleanup obligations.
