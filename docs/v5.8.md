## Delivery-ready owners

### PrintNightmare

The v5.8 owner is detection-first. A positive NetExec result establishes vulnerability evidence. An optional authorized-lab validation uses an operator-reviewed DLL and requires explicit driver/DLL-load output before execution is recorded. Neither detection nor execution silently becomes administrator or SYSTEM access.

### PrivExchange

PrivExchange is represented as an authenticated HTTP coercion primitive. Obol requires explicit Exchange-initiated authentication/callback evidence and keeps coercion separate from relay success, directory modification, and domain privilege.

### ProxyNotShell

The ProxyNotShell workflow uses a minimal `whoami` validation command. Explicit remote identity output establishes remote execution; SYSTEM is recorded only when the returned identity itself shows `NT AUTHORITY\\SYSTEM`.

### AppLocker bypass

The workflow first captures effective AppLocker policy and then verifies a reviewed trusted-binary path with a benign artifact that emits `OBOL_APPLOCKER_BYPASS_OK`. Policy discovery is not a bypass and bypassed execution is not privilege escalation by itself.

### Kerberos relay

The KrbRelayUp workflow separates the LDAP relay/control primitive, service-ticket material, and final SYSTEM proof. SYSTEM requires an independent identity readback from the temporary proof file and is never inferred from relay or ticket startup text.

## Release contract hardening

v5.8 adds `tools/validate-release-pr.js` and wires it into the required `test` job. Release PRs must come from the exact `release/obol-vX.Y` branch, carry an Obol release title, and include a substantive description with Summary, methodology accounting, Evidence boundaries, Release wiring, Regression coverage, and Compatibility sections.

The validator also checks release wiring in the repository itself. `tools/release-preflight.js` runs the repository-only contract before the release branch is moved, while the non-draft PR run validates the PR metadata and the complete historical regression chain.

Staging branches are build-only and must not remain open as competing release PRs. Once the release PR exists, its head must have a release-only commit so the protected `test` status is attached to a SHA that is not shared with a deliberately invalid staging PR. This prevents a staging-contract failure from contaminating the release PR's required-check state.

This directly closes the process failure that allowed an undescribed duplicate build PR to be merged for v5.7 and the shared-head status collision exposed during the v5.8 release.
