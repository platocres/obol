# Obol v9.18

Obol v9.18 continues Product Hardening by completing the canonical Certipy Tool Builder without adding a release-specific runtime layer.

## What changed

`tb-certipy` now exposes one schema-driven Certipy surface for the current upstream Certipy 5.1 command family:

- `find` for AD CS enumeration, vulnerable/enabled filtering, DC-only collection, issuance-policy OIDs, administrator-permission suppression, and stdout/JSON/text/CSV output;
- `req` for RPC, Web Enrollment, or DCOM certificate requests and retrieval, including CA/template, UPN/DNS/SID/subject, request-agent/renewal PFX, key archival, CAX certificate retrieval, output, and Web Enrollment transport controls;
- `auth` for PFX/P12 certificate authentication, optional username/domain override, ticket/hash behavior, Kirbi output, and certificate-authenticated LDAP shell mode;
- `relay` for AD CS HTTP/RPC relay targets, CA/template/SAN fields, output, listener controls, persistent relay behavior, and template enumeration;
- `shadow` for list/add/remove/clear/info/auto key-credential workflows with explicit cleanup actions;
- `account` for read/create/update/delete account operations and account attribute/password controls, including an explicit delete cleanup path.

The common Certipy target boundary exposes password, NT-hash, and Kerberos-cache authentication together with domain/user, target, DC IP/hostname, nameserver, and DNS transport context where the upstream subcommand accepts them. Certificate material is handled through mode-specific PFX fields instead of pretending every Certipy action has the same authentication shape.

## Upstream alignment

The builder was checked against the current `ly4k/Certipy` 5.1.0 parser definitions. The release deliberately models the current command names and options rather than preserving older Certipy syntax by memory.

## Proof boundary

Obol still does not execute Certipy. It builds and copies commands for the operator to run in an authorized environment. Enumeration labels, certificate requests, relay activity, shadow-credential changes, account mutations, PFX files, tickets, or recovered hashes become report-relevant only after the corresponding output is reviewed as Evidence. Recovered certificate or credential material remains candidate access material until independently validated.

## Compatibility

The stable Tool Builder owners remain `data/tool-builder-schema.js`, `assets/tool-builder-current.js`, `data/tool-builder-inventory.js`, and `data/tool-builders.js`. The live browser bridge remains `assets/app-v8.8.js`, and workspace schema compatibility remains v8.8. No `app-v9.18.js`, `core-v9.18.js`, `project-model-v9.18.js`, or release-specific stylesheet was added.
