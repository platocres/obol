# Obol v9.6 - Runtime Consolidation Foundation

v9.6 completes three same-ownership items from the recommended **Runtime Consolidation Foundation** package: `runtime-current-entry`, `runtime-data-manifest`, and `runtime-historical-equivalence`. The completed Orange 2025.03 methodology/source queue remains historical, closed, and regression-protected.

## One current runtime load authority

`data/runtime-manifest.js` is now the stable non-versioned owner for the ordered browser runtime and the Node current-runtime subsets.

Before v9.6, `index.html` hand-maintained the historical stylesheet and script chains while `tools/current-runtime.js` independently maintained Node DATA and CORE arrays. That duplicated load-order truth across separate surfaces and made future compaction riskier.

v9.6 changes ownership without deleting historical behavior:

- `index.html` loads `data/runtime-manifest.js` and the stable `assets/runtime-current.js` entrypoint;
- `assets/runtime-current.js` projects the manifest's styles and scripts in parser-blocking order during normal page bootstrap;
- `tools/current-runtime.js` projects its legacy `DATA` and `CORE` exports and execution order from the same manifest;
- historical CSS, domain, core, report, intake, and app files remain present and continue to execute where they still own behavior.

No `app-v9.6.js`, `core-v9.6.js`, `project-model-v9.6.js`, `obol-v9.6.css`, or other fake release-specific runtime overlay is introduced.

## Historical load-order equivalence

The pre-v9.6 runtime order is not treated as an undocumented implementation detail. `tests/fixtures/runtime-v9.5-load-order.json` freezes the v9.5 browser load contract at:

- 69 ordered stylesheets;
- 327 ordered scripts;
- stylesheet order SHA-256 `fb13446d915e59302b60cf6f51b524a99311f5e0807923a631a906b4929d781f`;
- script order SHA-256 `c31e4e1cb75c7a4496d01e0b28edf255d8045cfcba7e716ddd05122e87f5e26e`.

`tools/validate-runtime-manifest.js` permanently verifies those counts and fingerprints, rejects duplicate or missing manifest assets, proves the browser group projection equals the ordered manifest, proves Node core/data loading comes from that authority, and initializes the manifest-backed Node runtime to verify `C.VERSION` remains `8.8.0` with the current v8.8 project adapter available.

This is the safety boundary for later compaction. Future releases may replace historical layers only after their observable behavior has a regression-equivalent owner; they should not simply change the fixture to bless an unexplained load-order change.

## Asset integrity after manifest ownership

Moving hundreds of direct asset tags out of `index.html` could otherwise weaken missing-asset validation. `tools/validate-asset-references.js` now evaluates the stable runtime manifest and traverses its current and lazy asset references in addition to HTML, CSS, and supported dynamic browser references.

Release smoke therefore retains full local-asset coverage even though the entry HTML is intentionally much smaller.

## Product-hardening disposition

- `runtime-current-entry` is `complete`: browser and Node current runtime loading have stable non-versioned entry/ownership boundaries.
- `runtime-data-manifest` is `complete`: ordered load data has one manifest authority instead of duplicated hand-maintained chains.
- `runtime-historical-equivalence` is `complete`: the v9.5 ordered-load baseline and v8.8 runtime initialization are permanently gated before future historical-layer removal.

Architecture / runtime reaches **3/10 complete**. Overall Product Hardening reaches **10/632 complete**, with **64 queued** and **9 modeled** foundation items.

v9.6 intentionally leaves `runtime-css-consolidation`, `runtime-lazy-load-plan`, and `perf-bundle-budget` queued. Those require separate ownership/migration/performance work and are not declared complete merely because they share the broader package.

The next highest-priority live item is **CSS ownership consolidation**. The broader flat queue also places **Dashboard ownership consolidation** ahead of the later lazy-load item, so future agents should continue to use Product Build Next priority plus coherent package boundaries rather than blindly completing package members out of order.

## Permanent validation

Product Hardening preflight now includes:

```bash
node tools/validate-runtime-manifest.js
```

The release-specific regression suite is:

```bash
node tests/run-v9.6-tests.js
```

The v9.6 suite protects the three item dispositions and proof contracts, current manifest ownership, the v9.5 equivalence fixture, index/browser/Node projections, asset-validator manifest traversal, permanent preflight wiring, architecture/product-hardening documentation, and the no-fake-v9-runtime rule.

The exact release head remains authoritative: any change after a green preflight requires a new validated head before merge readiness.

## Compatibility

Obol remains static, browser-local, and human-run. v9.6 adds no backend, telemetry, account system, install prompt, automatic command execution, or public raw-note import. The v8.8 workspace/runtime schema identity remains unchanged, existing historical runtime files remain available, and Evidence/proof/report-readiness semantics are not altered.
