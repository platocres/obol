# Obol v9.40 — Runtime layer consolidation

v9.40 consolidates the live browser runtime. Every historical ownership area now loads through one stable, non-versioned owner instead of one request per historical fragment. The browser-local product contract is unchanged: no backend, no build step, no telemetry, no command execution.

## The problem

Obol grew by additive release overlay. Before this release the site loaded, on every visit:

- 236 historical scripts in the operator startup chain, one `<script>` per fragment;
- one stylesheet owner that then `@import`ed 69 more stylesheet fragments.

Measured in Chromium against a served checkout, Home fetched **321** JavaScript/CSS files. Evidence fetched 365. The ownership consolidation of v9.6–v9.31 had already given the runtime one manifest, one CSS owner, and current route owners, but the *delivery* was still one request per layer.

## What changed

Each ownership area gets one generated owner that is the **exact ordered concatenation** of its historical fragments:

| Ownership area | Fragments | Owner | Loading |
| --- | --- | --- | --- |
| Domain data | 103 | `assets/obol-domain-current.js` | operator startup |
| Core state and derivation | 69 | `assets/obol-core-current.js` | operator startup |
| Report base and application UI | 64 | `assets/obol-app-current.js` | operator startup |
| Evidence parsing | 41 | `assets/obol-evidence-current.js` | route-lazy |
| Nmap builders | 3 | `assets/obol-nmap-current.js` | route-lazy |
| Report overlays | 14 | `assets/obol-report-overlays-current.js` | route-lazy |
| Tool reference data | 3 | `assets/obol-tool-reference-current.js` | route-lazy |

`assets/obol-current.css` becomes the flattened cascade of its 69 fragments instead of an `@import` chain: 70 requests become 1.

Nothing is minified, reordered, wrapped, or rewritten. The same code runs in the same order in the same global scope. The historical fragments stay on disk as the frozen regression ledger, and the v9.5 order fingerprints are untouched.

| Next Steps | 329 | 27 |

## Why concatenation is safe here

Concatenating classic scripts is only equivalence-preserving if three hazards are ruled out, and `tools/validate-runtime-bundles.js` checks all three on every run:

1. **Strict-mode leakage.** A fragment carrying a `'use strict'` prologue would silently apply strict mode to every fragment after it in the same file. No bundled fragment carries one, and the generator refuses to bundle one that does.
2. **Automatic semicolon insertion.** Without an explicit terminator, a fragment ending in `foo()` followed by one starting with `(function(){…})()` parses as a single call expression. Every fragment is terminated with an explicit empty statement.
3. **Error isolation.** Separate `<script>` tags isolate load-time errors; one file does not. Every fragment and every owner is parsed independently, and the real-browser smoke suite fails on any console or page error.

Beyond those, the validator proves each owner is nothing but generated banners around verbatim fragment bodies, and runs the domain and core areas twice in isolated VM contexts — once as 173 fragment loads, once as 3 owner loads — asserting both produce an identical 236-symbol global surface.

## Proof

- `node tools/sync-runtime-bundles.js --check` — owners match their manifest fragments.
- `node tools/validate-runtime-bundles.js` — concatenation exactness, the three hazards, and the A/B global-surface diff.
- `node tools/validate-runtime-manifest.js` — frozen ledger, flattened cascade order, consolidated ownership coverage.
- `node tools/validate-runtime-loading.js` — consolidated request budget.
- `node tests/playwright-smoke.js` — real Chromium: per-route request ceilings, and failure if any historical fragment is fetched directly. The gate was confirmed real by running it against the pre-consolidation runtime, where every route fails.

## Dashboard and README

`data/runtime-consolidation-current.js` is the single projection for consolidation figures. The Product Hardening Dashboard and the generated README Product Build Next block both read it, and `tools/validate-runtime-consolidation-sync.js` fails when they disagree.

The dashboard also gets two layout repairs. The at-a-glance strip was reusing `.ph-hero`, whose fixed 240px first column crushed every tile into a character-wrapped sliver; it now has its own wrapping tile grid. The hero score panel stretched to the full height of the taller track grid, leaving a large empty box; it is now a compact full-width banner.

## What remains

Request consolidation is finished. **Semantic** flattening is not: the owners still concatenate 297 versioned fragments that override each other. Product Build Next now leads with one queued item per ownership area — domain, core, application, Evidence parsing, and stylesheet — each to be flattened on its own equivalence and workspace-migration proof, following the lifecycle in [`docs/RUNTIME-COMPACTION.md`](RUNTIME-COMPACTION.md). Do not flatten two areas in one pass.
