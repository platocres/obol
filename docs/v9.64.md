# Obol v9.64 pass-the-hash source re-mining

## Why this exists

The next selected note in `notes-batch-old-rubric-reviewed-remine-001` is the Pass-the-Hash note from the first HTB review packet.

This release re-mines that source into public-safe Obol behavior without copying private lab commands, target values, flags, hashes, usernames, reverse-shell payloads, screenshots, or exact solution chains.

## What changed

v9.64 adds `data/product-hardening/pass-the-hash-remining-v9.64.js`.

The extension adds four public field notes:

- `note-pth-is-protocol-scoped-auth-material`
- `note-pth-success-is-host-and-privilege-scoped`
- `note-pth-remote-exec-leaves-artifacts`
- `note-pth-local-admin-token-filtering-check`

It also registers three live card routes in the same release, so this build does not repeat the v9.62 ghost-card mistake:

```text
#/card/pass-the-hash-proof-chain
#/card/pth-remote-exec-artifacts
#/card/pth-token-filtering-check
```

The main card includes placeholder-based, human-reviewed command shapes for common PtH validation paths. These are generalized templates with Obol variables, not copied source commands.

## Ghost-card and path-placement repair

v9.64 also hardens the already-merged v9.63 visible-card repair.

The original v9.63 fix could install card objects after the route had already rendered `Unknown card`. The updated `visible-remine-cards-v9.63.js` now detects that state and repaints the current card route after the card exists.

The new `data/product-hardening/note-card-route-guard-v9.64.js` is a fail-closed runtime guard for note-derived card IDs. It discovers note-derived card IDs from public Field Notes and Product Hardening packets, creates a public-safe fallback card only when a referenced route would otherwise be dead, and repaints the current card route when needed.

The new `tools/validate-note-card-path-placement.js` covers the other half of the problem: cards must not merely exist. Current note-derived cards also need path-engine shape and Evidence linkage. The validator checks that required note-derived cards have `prereq`, `produces`, `expected`, and `lane` fields, and that their prereqs line up with Evidence facts or parent proof-chain activities.

## Evidence analyzer

The new `pass-the-hash-output-analyzer` classifies pasted terminal output into separate proof states:

- PtH attempt observed
- NT hash material observed
- Windows process/token path observed
- remote admin indicator observed
- remote execution artifact observed
- auth failure or lockout signal observed
- token filtering or restricted-admin condition observed
- local-account scope observed

The analyzer is intentionally conservative. A hash-shaped value does not become access by itself, and a successful login or remote execution result stays scoped to the observed identity, host, protocol, service, and privilege level.

A small dashboard-settle hook also ensures the runtime PtH state is applied before the Product Hardening Dashboard renders the re-mining totals.
