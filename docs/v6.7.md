# Obol v6.7 — ESC13 and ESC15 source-fidelity delivery

v6.7 resumes the live North Star Build Next queue after the v6.6 architecture consolidation. It converts the next three already-inventoried AD CS source units from broad-owner representation into explicit end-to-end Obol workflows: ESC13 issuance-policy/group-link template abuse, ESC15 Client Authentication application-policy injection for Schannel, and ESC15 Certificate Request Agent application-policy injection.

## Scope

The pinned 127-section canonical breadth denominator does not change in this release. Obol remains at 95 implemented, 32 partial, 0 gaps, 0 stale, 75% fully implemented, and 100% represented. The broad `adcs.template-misconfig` parent intentionally remains partial because other inventoried template-related atomic units still remain open.

Atomic AD CS source fidelity advances from 5/19 to 8/19 complete. Source inventory denominators remain 1/17 methodology files atomized and 7/34 frozen v6.2 partial baselines decomposed. The live Build Next queue therefore drops from 41 to 38 items: 11 remaining atomic source-fidelity audits followed by 27 source-inventory/decomposition items.

## Delivered source units

### ESC13 issuance policy / group link

`adcs-esc13-67` provides Kali and Windows request surfaces tied to explicit prior enumeration of the vulnerable template and issuance-policy relationship. Successful enrollment creates certificate material only. Obol does not infer group membership, PKINIT success, service access, administrator, SYSTEM, or compromise from issuance.

### ESC15 Client Authentication application-policy injection

`adcs-esc15-schannel-67` models the pinned-source Schannel branch using Certipy application-policy injection. The Client Authentication policy is part of the maneuver itself rather than an optional command toggle. A returned certificate is preserved as credential material plus a Schannel-specific certificate artifact; later Schannel service access requires separate Evidence.

### ESC15 Certificate Request Agent application-policy injection

`adcs-esc15-agent-67` models the request-agent branch and produces a distinct enrollment-agent certificate artifact. The artifact routes into the existing ESC3 on-behalf-of workflow. It does not establish the target identity, authenticated access, or privilege by itself.

## Evidence and reporting

All three workflows carry v6.7 Evidence profiles and report contracts. Terminal Evidence remains intentionally conservative: explicit certificate issuance or saved PFX material is required before the associated credential facts are proposed. Command recognition, request attempts, or template names alone do not create success facts.

Authenticated AD CS enumeration is also extended so explicit ESC13 and ESC15 observations can route the new branches through Next Steps. Project/source accounting metadata remains unable to create engagement facts.

## Architecture and release behavior

v6.7 preserves the v6.6 consolidation boundary rather than creating another project-wide status system. `C.projectModel67(...)` advances the current projection and remains compatible with the overview-first v6.6 Dashboard shell. Node-side status consumers continue through `tools/current-runtime.js`. Release surfaces remain delta-based.

## Validation contract

The release is validated through the existing tiered workflow: release smoke on ordinary pushes, current-release preflight on a coherent `[preflight]` snapshot, then the complete historical chain and permanent release-quality/synchronization gates on the exact `[release-final]` head. A later commit invalidates earlier merge-readiness and must be validated again.

## Compatibility

Obol remains static HTML/CSS/JavaScript with no backend, build step, telemetry, or automatic command execution. Browser-local state migration, sanitized export redaction, human-run command generation, Evidence review, Next Steps, reporting lineage, and the historical runtime remain compatible.
