# Obol v9.5 - Contrast and Focus Quality Pass

v9.5 completes the recommended **Contrast and Focus Quality Pass** Product Build Next package by closing `cc-link-contrast`, `ux-keyboard-focus`, and `qa-contrast-test`. The completed Orange 2025.03 methodology/source queue remains historical, closed, and regression-protected.

## Stable accessibility ownership

The release adds stable non-versioned accessibility owners rather than another v9 runtime overlay:

- `assets/accessibility.css` owns current workspace link, hover, focus-visible, forced-colors, and reduced-motion accessibility treatment after the historical CSS chain;
- `assets/accessibility.js` upgrades existing non-native clickable workspace surfaces for keyboard reachability and Enter/Space activation, synchronizes pressed state for toggle-like controls, and manages modal focus containment/restoration;
- `assets/app-v8.8.js` remains the current browser bridge because `C.VERSION` is still the v8.8 workspace/runtime schema identity, but it now loads the stable accessibility owners;
- `assets/product-hardening-dashboard.css` keeps the standalone and in-app Product Hardening Dashboard link/focus contract aligned with the same dark-theme accessibility targets.

No new `app-v9.5.js`, `core-v9.5.js`, `project-model-v9.5.js`, or `obol-v9.5.css` compatibility layer is introduced.

## Dark-theme link contrast

Current workspace links use explicit stable link tokens instead of inheriting historical dark-blue values from whichever layer happens to win the cascade. The deterministic accessibility validator calculates contrast for link and hover colors against the supported dark page, panel, and nested-panel surfaces and requires at least WCAG AA `4.5:1` contrast.

Focus indicators use a separate high-visibility token and are required to exceed `3:1` against the same dark surfaces. Links also gain underline/hover emphasis so state is not communicated by color alone.

## Keyboard and modal focus

Existing native controls keep their native semantics and receive visible `:focus-visible` treatment. Existing non-native clickable surfaces that predate the product-hardening phase are progressively enhanced at runtime rather than rewritten across dozens of historical layers.

The stable keyboard owner covers card headers, state cards, phase chips, variant/toggle chips, facts, progress/timer controls, lane tabs, and the dismissible banner control. Non-native surfaces receive `tabindex=0`, `role=button`, and Enter/Space activation only when they are not already native controls.

Open modals receive dialog semantics, initial focus inside the modal, contained Tab/Shift+Tab traversal, and focus restoration to the invoking control after close. Mutation observation keeps dynamically rendered route content and historical overlays inside the same accessibility contract.

## Permanent accessibility gate

`tools/validate-accessibility-contract.js` is the deterministic contrast/focus gate. It verifies:

- workspace and Product Hardening Dashboard link/hover contrast ratios;
- focus-indicator contrast and visible `:focus-visible` treatment;
- forced-colors support;
- stable accessibility asset loading from the live browser bridge;
- keyboard reachability and Enter/Space activation for existing non-native controls;
- modal dialog semantics, Tab containment, and focus restoration;
- existence and required route/viewport coverage in the screenshot-assisted QA checklist.

`tools/release-preflight.js` runs this validator for Product Hardening preflight/final releases so the v9.5 fixes remain permanent contracts rather than one-off release assertions. The validated preflight confirms this gate composes cleanly with current-release authority, version trust, product queue contracts, asset integrity, synchronization, release quality, and the existing historical-test safety boundary.

## Screenshot-assisted QA

`docs/visual-qa/contrast-focus.md` defines the representative route, viewport, link-state, keyboard-focus, and modal-focus screenshots/review states. Static contrast calculation remains the source of truth for numerical ratios; screenshot-assisted review catches composition problems such as clipping, inherited backgrounds, or visually weak focus rings that a ratio calculation cannot see.
