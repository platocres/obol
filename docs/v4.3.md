# Obol v4.3

Obol v4.3 is the **canonical reconciliation and cracking-contract audit** release.

v4.2 established a durable 127-section Orange Cyberdefense 2025.03 Active Directory denominator and deliberately validated every `implemented` mapping against live Obol methodology cards. That first pass also exposed an important truth: the canonical snapshot still under-counted several workflows that already existed elsewhere in Obol, and one RBCD mapping pointed at a legacy/nonexistent card ID.

v4.3 performs the next step the v4.2 README called for:

`canonical coverage → inspect live methodology → reconcile real implementations → keep partial work partial → update current coverage`

The release does not add a new primary navigation destination and does not make Obol autonomous. Obol remains static, browser-local, review-first, and human-run only.

## RBCD stale-mapping repair

v4.2 correctly exposed one stale canonical mapping in the Resource-Based Constrained Delegation section.

The old mapping referenced a nonexistent `rbcd` card ID even though Obol already had the workflow distributed across:

- `ad-machine-account-quota-v25` — readiness / machine-account precondition
- `delegation-abuse` — RBCD configuration and delegation workflow
- `getst-impersonation` — S4U payoff / ticket use

v4.3 replaces the stale reference with those live cards. The result is **0 stale implemented mappings** without creating a fake compatibility card.

The retained v4.1 tool-choice audit is also repaired so it no longer references the missing `rbcd` ID.

## Areas intentionally kept partial

v4.3 uses the stricter v4.2 completion semantics. Several areas are now represented but deliberately **not** counted as fully implemented.

### Authenticated known vulnerabilities

Obol has concrete GPP coverage and a safe Zerologon detection workflow, but the Orange authenticated-vulnerability container includes several additional historical branches. The container moves from gap to partial, not implemented.

### Zerologon

The existing `zerologon-check` card is detection-only. Obol intentionally does not call a destructive machine-account-password reset workflow complete merely to raise the percentage.

### Add Domain Admin and ACL persistence

Obol already has group-control and ACL-manipulation mechanics. Those generic capabilities are enough to represent the source nodes, but persistence lifecycle, proof, and cleanup semantics remain incomplete.

### SCCM PXE hash cracking

The Orange cracking source lists SCCM PXE AES material as mode 19850. Current real-world use still depends on a dedicated SCCM Hashcat module/fork rather than a normal stock Hashcat installation.

v4.3 therefore documents the mode but keeps `crack_hash.md → PXE / SCCM hash cracking` **partial**.

This is exactly the behavior required by the README North Star rule to evaluate whether an Orange tool path is actually the best and most user-friendly current path instead of copying it blindly.

## Execution-side metadata

v4.3 continues the v4.0/v4.1 requirement that Path and command presentation understand whether the operator is working from Kali or Windows.

Explicit execution metadata is added or repaired on the reconciled cards where the command side is high-confidence:

- Hashcat / NetExec / Nmap / Impacket / sccmhunter / smbclient / gpp-decrypt → Kali
- `nltest` / PowerView trust enumeration → Windows
- `nslookup` used for DC SRV discovery → neutral

The existing `operatorSurface40` mechanism remains the only execution-context contract. v4.3 does not create a competing platform system.

## Canonical provenance on cards

The v4.3 overlay attaches `orange43` provenance to live cards mapped from canonical sections.

Card pages can therefore show how many Orange 2025.03 canonical sections map to the current card and whether any of those mappings were reconciled in v4.3.

This makes the percentage traceable back to actual methodology instead of being a disconnected project metric.

## Next work after v4.3

The highest-value remaining canonical debt is now more honest and easier to prioritize.

Future releases should continue with:

- SCCM beyond reconnaissance: credential recovery, relay, takeover, execution, cleanup, and post-exploitation branches
- persistence beyond Golden Ticket: Silver Ticket, DSRM, Skeleton Key, Custom SSP, Golden Certificate, Diamond/Sapphire tickets, DCShadow, and persistence-specific ACL lifecycle
- trust abuse beyond enumeration and MSSQL links
- Windows low-access AppLocker/UAC/Kerberos-relay branches
- deeper AD CS branch-specific coverage
- relay/coercion depth, especially Kerberos relay
- authenticated historical-vulnerability coverage where it remains useful and safe to present as current lab methodology
- stronger transcript/Evidence fixtures for the newly reconciled cards
- continued explicit Kali-versus-Windows metadata audits

Keep the v4 information architecture small. New methodology should continue to live under existing ownership rather than becoming new primary navigation destinations.
