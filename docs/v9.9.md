# Obol v9.9 - Runtime Loading and Performance Budget

v9.9 completes the remaining **Runtime Consolidation Foundation** Product Build Next work by closing `runtime-lazy-load-plan` and `perf-bundle-budget` in one `runtime/build-loading` pass.

The release does not delete the frozen historical compatibility ledger. Instead, it separates that ledger from what has to execute on every ordinary workspace visit and creates a permanent budget for the default startup path.

## Route-aware runtime loading

`data/runtime-manifest.js` still owns the complete v9.5 compatibility script sequence of **327 historical scripts** and the **69 historical stylesheet fragments** used by the stable current CSS owner. Those full lists remain regression-observable and fingerprint-protected.

The manifest now also exposes a current `startupScripts` subset plus route-lazy groups. The reviewed v9.9 boundary removes **61 historical scripts** from default startup:

- **41 Evidence parsing assets** - JSZip, BloodHound helpers/patch, and versioned Intake parser overlays;
- **3 Nmap parser assets**;
- **14 historical report overlays** beyond the stable base report owner;
- **3 tool-reference data assets** for wordlists and scripts.

That leaves **266 historical scripts** in the default compatibility startup path.

`assets/runtime-current.js` loads the startup subset in preserved relative order. When the operator opens a route that needs a deferred group, the loader appends that group in its manifest order and rerenders the active route after hydration.

The route policy is intentionally conservative:

- Targets loads the Nmap group;
- Evidence / Artifacts load Nmap plus Evidence parsing;
- Tools loads tool-reference data;
- Report loads historical report overlays;
- Home and Next Steps do not request these route-local groups.

## Product Dashboard is actually lazy

The v8.8 compatibility bridge previously initialized Product Hardening queue/package/dashboard assets during ordinary startup even though project-build accounting had already moved out of the prime operator workflow.

v9.9 separates `ensureWorkflow88()` from `ensureProductAssets88()`. The stable `assets/workflow-current.js` owner remains available to Home and Next Steps, while Product Dashboard queue data, package metadata, dashboard stylesheet, and dashboard renderer are loaded only for `#/dashboard`.

This keeps the user-first workflow from paying the Product Dashboard loading cost until the dashboard is requested.

## Deliberate eager exceptions

The lazy-load plan records why some apparently deep surfaces are **not** deferred yet:

- methodology remains shared-core eager because Home and Next Steps ranking depend on it;
- lineage remains shared-core eager because Evidence, recommendation, and reporting semantics use it across routes;
- remaining historical behavior overlays stay compatibility-eager until a later compaction pass provides regression-equivalent replacement owners.

Those are explicit architectural exceptions, not forgotten optimization work. v9.9 prefers a smaller safe startup path over deleting dependencies whose observable contracts are still shared.

## Request and startup budget

`data/runtime-manifest.js` now carries the performance contract beside the loading model:

- frozen historical script baseline: **327**;
- default historical startup maximum: **266**;
- minimum deferred historical scripts: **61**;
- current CSS owner: **1** stable stylesheet, still projecting the preserved 69-fragment cascade.

`tools/validate-runtime-loading.js` permanently checks the reviewed lazy groups, route bindings, loading-policy exceptions, Product Dashboard startup behavior, and the 266/61 startup budget. A future release that silently moves one of these groups back into ordinary startup fails Product Hardening preflight.

This item is a runtime loading/request budget, not a claim that every CSS request or historical JavaScript file has been physically bundled. Further physical compaction can proceed later under the existing equivalence harness.

## Permanent validation

The new loading boundary and budget are checked by:

```bash
node tools/validate-runtime-loading.js
```

The existing runtime equivalence gate remains separate and still validates the complete historical compatibility ledger:

```bash
node tools/validate-runtime-manifest.js
```

The release regression suite is:

```bash
node tests/run-v9.9-tests.js
```

Product Hardening preflight runs the loading budget before the historical equivalence gate.

## Compatibility

Obol remains static, browser-local, and human-run. v9.9 adds no backend, telemetry, account system, install prompt, automatic command execution, public raw-note import, or workspace-schema migration. `C.VERSION` remains `8.8.0`.

The release does not change Evidence proof semantics, recommendation ranking, report lineage, browser-local workspace storage, or the frozen Orange baseline. The full v9.5 historical script order remains preserved as the compatibility ledger even though a reviewed subset now hydrates only when its route requires it.
