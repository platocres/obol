# Obol v5.0

Obol v5.0 is the **information-architecture, changelog, and UI/UX hygiene** release.

The release is driven by three requirements added after v4.9:

1. project-health metrics must live in one dedicated dashboard surface;
2. the README must stop acting as a release history and a maintained changelog must own that history;
3. the live UI must be reviewed for stale version labels, stacked release cards, old aesthetic leftovers, and North Star branding that leaks outside the allowed dashboard/Home surfaces.

v5.0 changes project presentation and release hygiene without inflating canonical methodology completion.

## Dedicated dashboard ownership

The five-item primary workflow remains unchanged:

- Home
- Targets
- Evidence
- Next Steps
- Report

`North Star Dashboard` is added under **More** at `#/dashboard`.

The full v4.9 project-health dashboard moves there. Home retains only a compact summary showing the two most important methodology numbers plus a dashboard link.

The dedicated dashboard remains the single in-app owner for project-wide percentages and hard denominators across:

- canonical methodology completion
- represented methodology coverage
- Run → Evidence loop readiness
- explicit Evidence-profile coverage
- mapped command execution-side metadata
- canonical decision-stage mapping
- reporting traceability
- structured tool-review status
- command UX counts
- active-context progress
- canonical backlog concentration
- release trend
- v5.0 UI/UX policy checks

## UI / UX policy accounting

`data/dashboard-v5.0.js` defines current presentation contracts.

`assets/core-v5.0.js` exposes `C.uiPolicyAudit50()` and `C.northStarDashboard50()`.

The dashboard reports hard pass counts for:

- exactly one dedicated Dashboard entry in More;
- exactly five primary workflow destinations;
- Dashboard/Home as the only allowed North Star brand surfaces;
- runtime version `5.0.0`;
- `CHANGELOG.md` as the release-history owner.

These checks are intentionally separate from methodology completion.

## Brand-surface cleanup

The user-facing Orange Cyber Defense name is intentionally limited to:

- the dedicated Dashboard;
- the compact Home dashboard summary.

Other live surfaces retain the underlying canonical methodology integration but use neutral wording such as `North Star`, `canonical methodology`, or `canonical source`.

This includes:

- Methodology;
- Next Steps;
- Report;
- mapped methodology cards;
- Guide;
- generated Standard and OSCP working drafts.

Source URLs and machine-readable provenance remain unchanged.

## Methodology cleanup

Methodology keeps the actual canonical file/section ledger and filtering controls.

v5.0 removes stacked project-health panels that duplicated Dashboard ownership, including old reconciliation and smaller audit-summary panels. A compact local note tells the operator that technique-level methodology remains here while project-health percentages live in Dashboard.

The canonical ledger itself is not removed.

## Guide cleanup

Historical `v4.x focus` cards are removed from the live Guide.

The v5.0 Guide is rewritten around the current operator workflow:

`Targets → Evidence → Next Steps → external command execution → Evidence → Report`

It links to the dedicated Dashboard for project health and to `CHANGELOG.md` for release history.

## README / changelog separation

`CHANGELOG.md` is created as the historical release record.

It contains release history from the v2 foundation through v5.0, including the major v3 and v4 architecture, Evidence, execution-context, coverage, SCCM, persistence, reporting, and dashboard milestones.

The README is rewritten to contain only:

- current purpose and architecture;
- current information architecture;
- current canonical status;
- permanent command/Evidence rules;
- permanent North Star requirements;
- current priorities;
- build-agent checklist;
- run/test/legal instructions.

Historical regression tests that previously treated README as a changelog are migrated to read `CHANGELOG.md` for release-history assertions while retaining permanent-requirement assertions against README.

## Report branding cleanup

`assets/report-v5.0.js` preserves all v4.7/v4.8 traceability and persistence-report sections but changes user-facing project-brand wording outside Dashboard/Home to neutral `North Star` / `canonical` terminology.

This does not change report evidence, proof, or finding semantics.

## Compatibility

v5.0 remains additive and browser-local.

It does not change:

- the 127-section canonical denominator;
- Evidence proof thresholds;
- activity success semantics;
- Next Steps applicability;
- Kali/Windows execution-context behavior;
- SCCM progression;
- persistence lifecycle;
- report readiness;
- sanitized export redaction.

The strict canonical baseline remains:

- 52 implemented
- 49 partial
- 26 gaps
- 0 stale
- 41% fully implemented
- 80% represented
