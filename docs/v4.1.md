# Obol v4.1

v4.1 turns the Orange Cyberdefense 2025.03 Active Directory mindmap from a README reminder into an auditable project-maintenance model.

The release is deliberately infrastructure-first. It does not claim that every mindmap branch is now implemented. Instead, it makes implemented, partial, gap, and stale-mapping states visible and machine-readable so future builds can stop relying on memory when deciding what remains.

Obol remains static, browser-local, review-first, and human-run only. Nothing in v4.1 executes commands, installs tools, scans targets, authenticates to systems, creates pivots, or converts methodology coverage into evidence.

## Coverage ledger

`data/methodology-v4.1.js` adds a machine-readable coverage registry with:

- Orange source area
- tracked node / technique family
- declared coverage state: implemented, partial, or gap
- linked Obol methodology card IDs
- Orange tools associated with the branch
- Obol-preferred tools
- tool-review decision: keep, supplement, replace, or review
- a short rationale

`assets/core-v4.1.js` validates that model against the live methodology data and exposes:

- implemented / partial / gap / stale counts
- explicit completion percentage
- audited percentage
- mapped card IDs
- source-file inventory
- priority gap queue
- tool-review summary
- execution-metadata audit summary

A declared implemented node whose linked card later disappears is surfaced as a stale mapping rather than silently counted as complete.

## Methodology UI

The existing Methodology surface owns the coverage ledger. v4.1 adds no primary navigation item.

The Methodology page now shows:

- current implemented / partial / gap totals
- explicit completion percentage
- audited execution-metadata percentage
- highest-priority audit debt
- filter by implemented / partial / gap / stale
- optional tool-review details
- direct source links to the Orange markdown container
- mapped Obol cards for each tracked node

This is project-methodology context, not engagement evidence.

## Tool evaluation

The v4.0 README added a requirement to consider whether the tools in the Orange mindmap remain the best and most user-friendly choices.

v4.1 gives that requirement a structured home.

Initial review decisions include examples such as:

- keep Nmap + NetExec for discovery/profiling
- keep NetExec as the preferred compact SMB/LDAP workflow while retaining enum4linux-ng/smbclient fallbacks
- supplement `dig` with dnsrecon for structured DNS work
- keep both Kali and Windows AS-REP / Kerberoast implementations
- supplement Orange remote-execution choices with NetExec for quick validation and Evil-WinRM for interactive WinRM
- retain Impacket and mimikatz as important credential-dump fallbacks while allowing NetExec to remain the concise remote option
- explicitly mark PXE/NAA, TimeRoasting, SCCM, and domain-persistence branches as review/gap work rather than pretending they are covered

Tool decisions do not delete alternative commands. They are methodology maintenance guidance.

## Explicit execution-side metadata

v4.0 introduced conservative execution-side inference for Kali, Windows, target-local, and neutral implementations.

v4.1 starts replacing that inference with audited metadata.

For commands linked to the initial Orange coverage ledger, high-confidence tool/variant contracts can now receive explicit `operatorSurface40` metadata plus an `operatorSurface41Source` marker.

Examples include:

- NetExec / Impacket / Certipy / BloodHound Python → Kali
- Rubeus / mimikatz / SharpHound / PowerView / native PowerShell AD tooling → Windows
- clearly local Linux shell enumeration → target-local

The v4.0 runtime already gives explicit `operatorSurface40` metadata precedence over inference, so v4.1 improves the existing ranking/guidance behavior without introducing a second execution-context system.

Commands that have not been audited continue to use the conservative v4.0 fallback.

## Coverage baseline

The initial ledger intentionally contains all three states:

- implemented work such as Nmap discovery, anonymous SMB/LDAP, AS-REP roasting, BloodHound collection, remote execution, ticket reuse, credential dumping, and DCSync
- partial work such as poisoning/coercion depth, ACL abuse breadth, delegation variants, AD CS breadth, and domain-compromise coverage
- explicit gaps such as PXE/NAA, TimeRoasting, SCCM, and domain-persistence branches

The point is not the initial percentage. The point is that future releases now have a durable place to move nodes from gap → partial → implemented and to record why.

## Remaining priorities after v4.1

- expand the Orange registry from major containers into finer technique-level nodes
- convert more inferred execution-side classifications into audited explicit metadata
- review the newly exposed PXE/NAA, TimeRoasting, SCCM, persistence, delegation, and AD CS gaps one by one
- keep validating Rubeus and other CLI contracts against upstream releases
- continue broader Evidence/full-session regression work
- deepen exact activity lineage and compromise-path chronology
- expand route-specific pivot troubleshooting and proof-readiness templates
- keep the v4 information architecture small

The coverage ledger should be updated alongside methodology code in future releases rather than treated as optional documentation.
