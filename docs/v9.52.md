# Obol v9.52

v9.52 starts actual full-spectrum source re-mining, hardens the release-identity synchronization contract that the previous release shipped stale, and declutters the README into an action-first handoff.

## Windows privilege-escalation source re-mining

This release begins the re-mining gate that v9.51 scaffolded. All 15 already-reviewed Windows privilege-escalation notes were re-read from the original private ENEX sources — not the public Field Note, prior rationale, prior disposition, or output IDs — and scored against every extraction dimension.

The audit rows live in `data/product-hardening/note-progress-current.js` (`remining.auditRows`), one row per note with an original-source-reread confirmation and a per-dimension outcome. Outcome and dimension counts are computed from the rows, never hand-maintained, so `tools/validate-note-remining-audits.js`, the dashboard, and the audit trail cannot drift. The batch resolved to 7 `added`, 114 `covered`, 16 `queued`, 17 `private-only`, and 86 `not-applicable` decisions, with zero red flags.

Re-mining surfaced one genuinely missed, public-safe capability and added it additively to the existing Orange Windows local-privilege path node: the Field Note `note-windows-service-trigger-tool-proof`. A writable service binary, unquoted service-path candidate, modifiable scheduled task, or hijackable DLL location is only a lead until trigger capability (restart rights, or automatic start plus a reboot privilege) and ACL intent are proven, and automated helpers (PowerUp, WinPEAS, Seatbelt) are leads that can be anti-virus-blocked or false-negative. The note is wired to the actual Next Steps / Orange path surface and to the `powershell`, `icacls`, and `winpeas` tool contexts. The frozen v9.35 Windows packet and its milestone are unchanged.

Two product gaps the re-mining surfaced are filed as `queued` outcomes: a terminal-output analyzer for service/ACL and `whoami /priv` output, and operator logging-exposure (PowerShell Transcription / Script Block Logging) report and cleanup guidance.

## Release-identity synchronization hardening

v9.51 shipped three stale release-identity artifacts. This release fixes them and closes the gap that let them ship:

- The v9.50 test hard-coded the README current-release token; it is demoted to a version-agnostic check.
- The v9.51 test hard-coded README, `index.html` shell, and `data/current-release.js` literals; they are demoted to a version-agnostic release-identity synchronization invariant.
- The generated `assets/obol-app-current.js` still inlined v9.50; it is regenerated from the current release authority.
- The missing v9.51 CHANGELOG entry is restored.

`tools/validate-historical-tests.js` now also rejects hard-coded `index.html` release-shell tokens (`<title>Obol vX.Y — …` and the `Offensive Box Operations Ledger · vX.Y` tagline) in historical suites, so a future release cannot ship a test that pins the mutable site shell.

## README declutter and agent workflow

The README is decluttered into a current-state, action-first handoff with a `Continue developing (start here)` section, and the detailed build loop — including raw-source note re-mining mechanics (`git lfs pull` of the private ENEX bodies) — moves into the new `docs/AGENT-WORKFLOW.md`. The README and the Product Hardening Dashboard still read the same queue data, so the generated Product Build Next block stays in sync with the dashboard.

## Validation

The permanent notes-impact and re-mining checks are `node tools/validate-notes-impact.js`, `node tools/validate-note-integration.js`, `node tools/validate-note-remining-audits.js`, `node tools/sync-product-build-next.js --check`, and `node tests/run-v9.52-tests.js`. Release-identity and historical-test future-safety are validated by `node tools/validate-current-release.js`, `node tools/validate-historical-tests.js`, and `node tools/validate-readme-history-ownership.js`. CI owns the complete historical regression chain and deep browser proof on `[full-regression]` heads; `[release-final]` is not a CI trigger.
