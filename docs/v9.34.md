# Obol v9.34

v9.34 hardens the Product Hardening Dashboard so current-state data cannot remain silently pinned to a previous release after rapid GitHub Pages updates, browser caching, or a long-lived Obol tab.

## Build scope

- Keeps `assets/dashboard-route-current.js` as the stable Dashboard route owner rather than introducing another versioned Dashboard layer.
- Removes the stale-global readiness shortcut as a freshness boundary. Existing in-memory globals are no longer treated as proof that the Dashboard inputs match the repository currently served by GitHub Pages.
- Refreshes the complete current Dashboard asset set on every Dashboard activation using cache-busted `obol-dashboard` generations.
- Refreshes the Dashboard stylesheet through the same generation so presentation fixes do not lag behind data fixes.
- Makes the stable Dashboard route owner self-refresh through an `obol-current` request when it was reached through the ordinary unversioned runtime URL. A newly fetched owner instance supersedes the older instance and becomes the only active route/repair owner.
- Stamps rendered Dashboard shells with the authoritative release and freshness generation for browser proof and troubleshooting.
- Reworks `product-hardening.html` to consume the same current Dashboard route loader instead of maintaining a second static list of Dashboard scripts and styles.

## Why the Dashboard became stale

The Dashboard retirement work correctly removed historical Dashboard data and presentation layers from live startup, but the current route owner still made two assumptions that were unsafe for a fast-moving static site.

First, it considered an already-present global such as `OBOL_PRODUCT_HARDENING_NOTES_IMPACT` or `OBOL_CURRENT_RELEASE` sufficient readiness. In a tab that had opened an earlier Dashboard, those globals could remain valid JavaScript objects while being obsolete repository state.

Second, current Dashboard inputs were fetched through stable unversioned GitHub Pages URLs. When releases were merged close together, a browser or intermediary cache could legally reuse the previous response for the same path. The README and `main` could therefore be at v9.33 while the Dashboard still rendered an older current-owner projection.

v9.34 changes the contract from "current owner exists" to "current owner has freshly loaded the current asset generation."

## Freshness contract

Each Dashboard activation now:

1. creates a new generation token;
2. fetches the current Dashboard stylesheet with that token;
3. sequentially fetches current release authority, Product Hardening queue/work packages, note-integration layers, note-progress/impact projections, and the Dashboard renderer with the same token;
4. verifies every script initialized its expected public owner;
5. records the successful generation in `window.__OBOL_CURRENT_DASHBOARD_FRESHNESS__`;
6. renders only after the refreshed owners are available.

A later activation repeats the process with a different token. This is intentionally more aggressive than the rest of Obol's static caching because the Dashboard is a development/control surface and its asset set is small relative to the historical compatibility runtime.

## Browser regression proof

The Playwright smoke now treats freshness as part of the permanent Dashboard contract. It loads the Dashboard, records the authoritative release and Notes Integration review count, deliberately replaces those globals with stale values, reactivates the Dashboard, and requires the current values to be restored by a distinct cache-busted generation.

The smoke also requires a cache-busted current route-owner request and verifies that the standalone Dashboard converges on the same route owner and freshness projection as `#/dashboard`.

## Product boundaries

- Obol remains a static, browser-local website.
- No backend, account, telemetry, automatic exploitation, or automatic command execution is added.
- No historical Dashboard runtime layer is restored.
- No second Dashboard data model or queue is introduced.
- Product Build Next remains sourced from the existing Product Hardening queue and work-package owners.
- The corrective release does not inflate the queue denominator simply to represent a bug fix.
