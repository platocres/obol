# Obol v9.4 - Version Trust Surfaces

v9.4 completes the recommended **Version Trust Surfaces** Product Build Next package by closing `cc-report-version` and `qa-version-test`. The completed Orange 2025.03 methodology/source queue remains historical, closed, and regression-protected.

## Report product identity

Historical report generators legitimately retain historical implementation and workspace-schema behavior, but their final product-facing version text must not leak stale release labels into a current report.

`data/current-release.js` remains the single current product-release authority and now also exposes stable identity helpers:

- `stampState(...)` stamps current `obolRelease` and `obolReleaseLabel` metadata on live/sanitized state without changing workspace schema identity;
- `normalizeReportMarkdown(...)` replaces report-owned historical Obol metadata/footer labels with the current product release;
- report normalization is intentionally narrow: operator-provided Evidence/code-block text and whitespace are preserved verbatim even when they contain historical-looking Obol strings;
- header normalization stops before report sections or fenced Evidence, and footer normalization is fence-aware, so release cleanup cannot mutate recorded operator content;
- normalization is idempotent so preview/export paths can safely pass through the same contract more than once.

`assets/app-v8.8.js` remains the current browser bridge because `C.VERSION` is still the v8.8 workspace/runtime compatibility identity. The bridge consumes `OBOL_RELEASE_IDENTITY` rather than maintaining duplicate report/export release logic.

## Permanent version identity gate

`tools/validate-version-identity.js` is the permanent product-version trust gate. It proves that:

- README current release agrees with `data/current-release.js`;
- browser tagline/title/settings presentation derives from the current release authority;
- the final report generator is wrapped by current report normalization;
- stale report-owned historical version metadata is removed;
- report footer identity uses the current product release;
- operator Evidence containing historical-looking version text and deliberate whitespace is not rewritten;
- sanitized export metadata carries the current product release;
- the v8.8 workspace schema identity remains distinct;
- standalone and in-app Product Hardening Dashboard presentation continues to consume the current release authority.

`tools/release-preflight.js` now runs this validator for every Product Hardening preflight/final release, so the `qa-version-test` completion is not only a v9.4 one-off test.

## Product-hardening disposition

`cc-report-version` is `complete` with item-specific acceptance criteria, validation commands, and proof files. `qa-version-test` is also `complete` with its own permanent regression contract.

Critical correctness advances to 3/4 complete. Testing / visual QA records its first completed item. Product Build Next advances to `cc-link-contrast` and the recommended **Contrast and Focus Quality Pass** package, which also includes `ux-keyboard-focus` and `qa-contrast-test`.

## Historical regression boundary

The v9.3 suite was made future-safe as part of this release. It still proves the v9.3 asset-integrity and coherent-work-package milestones, but it no longer requires the mutable current queue to remain parked on the Version Trust package after v9.4 completes it.

Historical report files are not rewritten merely to erase old implementation labels. Current product identity is normalized at the stable final-release boundary while historical files remain valid regression fixtures.

## Validation

The v9.4 package is protected by:

```bash
node tools/validate-version-identity.js
node tools/validate-current-release.js
node tools/validate-product-hardening-queue.js
node tools/validate-asset-references.js
node tools/sync-current-release.js --check
node tools/sync-product-build-next.js --check
node tools/validate-release-pr.js --repo-only --release-version=9.4
node tests/run-v9.4-tests.js
```

The coherent preflight snapshot passes the version-trust gate while preserving fenced Evidence. The exact `[release-final]` head remains the authoritative merge-readiness snapshot and must pass smoke, preflight, and the complete historical regression chain required by `BUILDING.md`.

## Compatibility

Obol remains static, browser-local, human-run, and free of backend, telemetry, account, install, or automatic-command-execution dependencies. v9.4 does not change Evidence/proof semantics, does not change the v8.8 workspace/runtime schema identity, does not reopen Orange source work, and does not add a versioned v9 runtime overlay.
