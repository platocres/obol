# Obol v10.01

Product-hardening release v10.01 completes the Post-mining Tools builder-library cleanup.

## Summary

This build turns the Tools route into a grouped Tool Builder Library without taking away direct manual tool selection. The operator can still open a tool directly with `#/tools/<tool>`, but the selected tool route now prioritizes the implemented schema-driven builder, tool-specific accessories, pickable modes/presets, and then collapsed related cards or legacy command examples.

The important premise is explicit: Tools is where the operator says, "I know the tool I want, help me build the right command." Path and Card remain the evidence-ranked "tell me what to do next" surfaces.

## What changed

- Restored the historical `assets/app-v2-tools.js` fragment so the generated current application bundle stays stable, then moved the new Tools experience into a lazy current Tools owner.
- Replaced the tab-per-tool expanded matching-card dump with a grouped Tool Builder Library where direct `#/tools/<tool>` selection remains first-class.
- Promoted implemented schema-driven builders, generated command previews, pickable modes, and tool-specific accessories before related cards or legacy examples.
- Made ffuf-style fuzzing accessories explicit: web-content, vhost, and parameter wordlists plus filters, headers, cookies, recursion, threads, and output controls.
- Made cracking accessories explicit for Hashcat and John: rockyou.txt, hash modes, rules, masks, workload/output controls, and `--show` behavior.
- Kept Nmap, NetExec / `nxc`, and Ligolo-ng explicit in the library model instead of hiding them under generic discovery, AD, or pivot language.
- Canonicalized NetExec display so `nxc` is the single visible launcher while `netexec` remains an alias route for compatibility.
- Kept related card commands available behind deliberate drilldown instead of deleting them or letting them dominate the selected tool route.
- Added focused Node and browser validation for direct tool selection, implemented-builder-first rendering, first-class accessories, hashcat/ffuf behavior, Nmap/nxc/Ligolo-ng visibility, NetExec alias de-dupe, and matching-card-dump retirement.

## Tools, Path, Card, and Evidence contract

Tools, Path, and Card should share the same command-building primitives, but they do not have the same job.

Tools is the direct manual launcher. The operator already knows the tool they want, selects it from the library, picks modes/accessories, generates a command, runs it externally, and pastes output back into Evidence.

Path is the evidence-ranked recommender. It looks at observed facts, blockers, credentials, routes, and produced evidence, then tells the operator what should happen next. Path may point to a Tool route or a Card, but it should not invent a separate command-building system.

Card is the technique/context surface. It explains why the action matters now, shows the primary command or GUI action, exposes expected evidence and outcome controls, and links related tooling.

Shared across those surfaces: the tool-builder schema, generated command preview, copy/review behavior, accessory vocabulary, wordlist/rule/mask references, Evidence paste-back guidance, and human-run proof boundary. Not shared: Tools direct browsing state, Path ranking/priority decisions, and Card-specific why-now/technique explanation layout.

## Modeled tool backlog

A tool marked `modeled` is not done. It means Obol recognizes the tool, keeps it visible, preserves aliases and related examples, and knows where it belongs, but it does not yet have a full implemented schema-driven builder.

The v10.01 cleanup now makes that explicit with `post-notes-tool-builder-implementation-backlog`. That follow-up item is queued after the visual density regression pass so future builds can graduate modeled tools into implemented builders in batches. Each modeled tool must either become implemented, be deliberately superseded by another implemented builder, or be explicitly rejected with rationale.

The high-value backlog starts with operator-critical tools and families such as Ligolo-ng, hydra, kerbrute, BloodHound collection, smbclient/smbmap, enum4linux-ng, ldapsearch, responder, linpeas/winpeas, msfvenom/msfconsole, nc, Penelope, and common file-transfer helpers. Nmap and NetExec / `nxc` are already explicit implemented surfaces and should continue to improve through the same shared builder/accessory contract.

## Compatibility

Obol remains static and browser-local. No backend, account system, telemetry, install prompt, or automatic command execution was added. Generated commands remain human-reviewed and externally run. Evidence and report proof boundaries remain visible.

Existing related card commands are not deleted. They are moved behind deliberate drilldown on the selected tool route so implemented builders and relevant accessories are the primary experience.
