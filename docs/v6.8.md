# Obol v6.8

v6.8 continues the North Star source-fidelity queue with the next three already-inventoried AD CS units: ESC4 writable certificate-template ACL, ESC7 Manage CA officer transition, and ESC7 Manage Certificates enable / request / issue / retrieve.

The release also closes a source-accounting reconciliation gap left deliberately conservative in v6.7. Canonical parents advance only when every inventoried subordinate source unit under that parent is fidelity-complete.

## Source-fidelity delivery

### ESC4 writable certificate-template ACL

`adcs-esc4-68` gives ESC4 a dedicated reversible workflow instead of relying on the broad AD CS/ACL owner.

The pinned Orange source preserves the technique as template modification followed by ESC1 and later restoration. v6.8 keeps that decision path but modernizes the operator surface to current Certipy template-management semantics:

- save the current configuration before mutation;
- write the default ESC1-compatible configuration only after the operator reviews the generated command;
- treat successful update output as template-mutation proof only;
- route the resulting `adcs.esc4_template_modified` fact into the existing dedicated ESC1 owner;
- restore the exact saved configuration as a separate cleanup action;
- preserve restoration as explicit cleanup Evidence rather than erasing the historical activity.

Kali/password and Windows/current-logon surfaces are both represented. Optional network, DNS, debug, and confirmation behavior stays in semantic controls instead of opaque one-liners.

### ESC7 Manage CA officer transition

`adcs-esc7-manage-ca-68` models the Manage CA stage as a distinct role transition:

- add the authorized test principal as certificate officer only when explicit enumeration supports Manage CA;
- record only explicit successful officer assignment;
- route that fact to the separate Manage Certificates chain;
- remove the officer assignment as cleanup only when the test introduced it.

Officer assignment is CA configuration state. It is not certificate issuance, authenticated access, administrator privilege, or compromise proof.

### ESC7 Manage Certificates request chain

`adcs-esc7-manage-cert-68` keeps the source's multi-stage behavior explicit instead of flattening it into one success state:

1. enable the reviewed template only if the authorized path requires publication and the template was not already enabled;
2. submit the target certificate request;
3. when the CA denies enrollment but returns a request ID and saves the matching private key, record only a pending-request fact;
4. issue the specific preserved request ID;
5. retrieve that request and require explicit certificate/private-key output before creating certificate-material facts;
6. disable the template only if the test enabled it and that action restores pre-test state.

A request ID is not a certificate. An issued request is not certificate possession. Certificate possession is not authenticated service access. Access is not administrator or SYSTEM privilege.

## Evidence and reporting

v6.8 adds conservative Intake handling for the delivered cards and their individual stages. Supported facts remain deliberately narrow:

- ESC4 template modified / restored;
- ESC7 officer added / removed;
- ESC7 template enabled / disabled;
- ESC7 pending request;
- ESC7 request issued;
- retrieved certificate material.

No v6.8 parser creates administrator, SYSTEM, foothold, cross-domain, or domain-admin facts from these stages.

All three owners use the existing Evidence profile and report-contract infrastructure so preserved activity, exact commands, Evidence, cleanup state, and report-ready claims remain traceable.

## Architecture

v6.8 keeps the delta-based release architecture established in v6.6 and introduces one small consolidation improvement: `C.currentProjectModel(...)` is now the stable non-versioned pointer for current project-status consumers. The v6.8 implementation is `C.projectModel68(...)`.

README synchronization and release-quality tooling now prefer the stable pointer. Historical versioned adapters remain available for regression history. The existing overview-first Dashboard shell remains in place rather than creating a new Dashboard owner for version symmetry.

The v6.7 UI overlay is also made future-safe so its title/tagline observer becomes inactive when a later core version is current.

## Tool suitability review

The pinned Orange source remains the technique/provenance owner, but its ESC4/ESC7 examples predate current Certipy CLI naming. v6.8 reviewed the current Certipy v5 template, CA, and request interfaces before delivery and uses current `-write-default-configuration`, `-write-configuration`, officer-management, template publication, request issuance, `-retrieve`, `-sspi`, and related semantic options where they preserve the same source maneuver more accurately for today's operator workflow.

The release deliberately does not preserve stale switch names merely for source-text symmetry. The source branch, prerequisites, outcomes, proof boundaries, and cleanup obligations remain pinned; the operator surface is reviewed for current suitability as required by the North Star contract.

## Compatibility

Obol remains plain static HTML/CSS/JavaScript with no backend, build step, telemetry, scanning, authentication, exploitation, command execution, or tool installation. Commands are generated for a human operator to review and run externally in an authorized environment.

Existing browser-local workspace migration, sanitized export, proof boundaries, report lineage, Next Steps behavior, source denominators, and historical regression ownership remain compatible.
