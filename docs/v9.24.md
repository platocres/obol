## Manual Outcome model

Manual Outcomes represent operator-reported workflow state separately from Evidence proof state. The model keeps `tried` plus four explicit outcomes: `success`, `failed`, `blocked`, and `skipped`.

Each record preserves the action/card or queued-intent identity, active context, timestamp, reason/note, outcome history, Evidence references, and whether the assertion still `needsEvidenceForReport`. New records are always unproven. A caller cannot create a supported outcome merely by supplying an Evidence-looking string.

Failure and blocker triage supports the common reasons `auth-failed`, `timeout`, `no-results`, `syntax-issue`, `blocked`, `not-vulnerable`, and `other` so an unsuccessful attempt can drive a retry or alternate route without being confused with proof of vulnerability or access.

## Workflow advancement without proof laundering

A user-declared success can advance the live workflow. For cards with expected `produces` facts, the operator chooses what the action actually established. Obol may add those selected facts as low-confidence provisional workflow facts whose provenance is `manual-outcome:<outcome-id>`. Existing Evidence-backed facts are never replaced or downgraded by a later manual assertion.

Those provisional facts may recalculate Path and unlock expected Next Steps immediately. The matching activity can also appear as succeeded in the live workspace. That is workflow convenience, not a report-proof shortcut.

Before report generation, `projectReportState(...)` creates a report-only state projection. Unsupported manual successes are changed out of the report generator's normal success path, and unsupported provisional manual facts are removed from that projection. The live workspace is not mutated.

## Reviewed Evidence boundary

A manual outcome becomes supported only when it is explicitly linked to an existing reviewed non-manual Evidence fact. `attachEvidence(...)` rejects invented labels, system/manual facts, card assertions, migration placeholders, and other manual-outcome facts. The referenced fact must already exist in the workspace with a non-manual Evidence source and an Evidence excerpt.

The card UI therefore asks for a **Reviewed Evidence fact ID**, not arbitrary supporting text. Until that link succeeds, the outcome remains `UNPROVEN — needs Evidence` for reporting.

Generated report drafts include a `Manual Outcomes` section. Unsupported rows remain visibly unproven. Supported rows retain the linked Evidence fact IDs for lineage. Reviewed Evidence remains the authority for report-ready findings and facts.

## Card and queue integration

Every rendered runnable methodology card identified through the stable `[data-cardroot]` contract receives four controls:

- Mark successful
- Mark failed
- Mark blocked
- Mark skipped

The older tried/success controls are hidden on runnable cards so they cannot bypass the v9.24 proof boundary. Reset and Evidence/Intake workflows remain available.

The implementation is generic and does not contain lab names, target recipes, or card-specific branches. `coverageForCards(...)` gives every card with executable commands the `manual-outcome` disposition and marks non-executable cards separately.

Queued human intent also survives outcome changes. A queued item records its attempt count, latest outcome, outcome time, proof requirement, and completed/failed/blocked/skipped state instead of being silently deleted when Path reorders. The stable workflow queue remains independently focusable and removable by the operator.
