# Obol v6.9

v6.9 continues the already-inventoried AD CS source-fidelity queue from v6.8. It delivers ESC5 PKI-object / CA-key control, ESC6 CA SAN flag identity selection, and ESC11 RPC/ICPR enrollment relay as explicit end-to-end operator workflows while preserving Obol's static, browser-local, human-run architecture.

## Scope

The release converts three existing atomic source units from broad-owner representation to fidelity-complete modeled outcomes:

- `adcs.esc5` — vulnerable PKI-object ACL / CA-key path
- `adcs.esc6` — CA SAN flag identity-selection path
- `adcs.esc11` — RPC/ICPR enrollment relay

The pinned Orange 2025.03 denominator remains unchanged. Source-fidelity delivery is credited only after the full North Star contract is accounted for: source structure, branch conditions, tool review, semantic command surface, execution context, Evidence, Next Steps, reporting, cleanup applicability, and explicit terminal disposition.

## Canonical reconciliation

v6.9 advances two broad canonical parents only because every currently inventoried subordinate unit under those parents is now fidelity-complete:

- `adcs.pki-object-acl` advances after ESC5 is complete.
- `adcs.ca-misconfig` advances after ESC6 and ESC11 are complete.

Canonical methodology therefore moves to 99 / 127 implemented, 28 partial, 0 gaps, 0 stale, 78% strict completion, and 100% represented. The frozen v6.2 34-section source-depth denominator remains unchanged.

## Operator workflows

### ESC5

The workflow separates CA backup material from forged certificate material. Explicit CA backup output creates only the CA-key-material fact. An offline forge step may then create certificate material. Neither stage proves authenticated access, administrator, SYSTEM, DCSync capability, or compromise.

The preferred operator surface is current Certipy. Kali uses explicit credentials; Windows may use SSPI for the CA backup step. The forge operation remains an offline artifact transformation regardless of operator OS.

### ESC6

The workflow requires prior Evidence that the reviewed CA allows requester-controlled SAN attributes and that a suitable client-authentication-capable template is available. A successful request produces certificate material only. Authentication and service access remain separate activities.

Both explicit-credential Kali and SSPI Windows request surfaces are represented.

### ESC11

The workflow models RPC/ICPR enrollment relay with Certipy as the preferred compact surface and ntlmrelayx as the pinned-source-compatible fallback. Listener startup and inbound authentication are not certificate issuance. Only explicit returned certificate material advances the workflow. A later certificate-authentication step remains separate and does not imply DCSync capability or privilege.

## Evidence and reporting

v6.9 adds dedicated Evidence profiles and reporting contracts for all three owners. Intake recognizes distinct ESC5 backup/forge and ESC11 relay stages and preserves the existing proof separations between sensitive artifacts, credential material, authenticated access, privilege, and objectives. ESC6 certificate Evidence is accepted only when the activity is already associated with the dedicated ESC6 owner, avoiding ambiguous remapping of generic certificate requests that can resemble other AD CS branches.

Enumeration output can route to ESC5, ESC6, and ESC11 only when those identifiers are explicitly present in reviewed Evidence.

## Architecture

v6.9 continues the delta-based release model. The release adds only the behavior-specific methodology, fidelity, project-model, core, Intake, UI, CSS, tests, and release documentation required for this wave. It keeps `C.currentProjectModel(...)` and `C.currentNorthStarDashboard(...)` as stable current pointers while retaining versioned adapters for historical regression boundaries.

The v6.8 UI overlay becomes inactive when a later release owns the current version surface, preventing historical title/tagline and Dashboard decorators from fighting v6.9.

## Validation contract

Merge readiness follows `BUILDING.md`: one draft release PR, smoke on ordinary pushes, coherent `[preflight]`, then an exact `[release-final]` head with smoke, preflight, the complete historical regression chain, release-quality validation, repository release-contract validation, and README Build Next synchronization all green. Any commit after the final validated head invalidates release readiness until validation is repeated.

## Compatibility

Obol remains plain static HTML, CSS, and JavaScript with no backend, build step, telemetry, autonomous command execution, scanning, authentication, exploitation, or tool installation. Existing browser-local workspace migration, sanitized exports, human-run command generation, conservative Evidence interpretation, Next Steps behavior, reporting lineage, and source-accounting denominators remain compatible.
