# v9.55 card evidence flow, OS routing, and Windows privilege re-mining

This hotfix closes three product gaps found during visual inspection after v9.54.

## Card-scoped evidence flow

Card evidence must not feel detached from the card that produced it. When a user clicks `Analyze pasted evidence` from a card, Obol preserves the originating card ID, card title, last copied command, and current context in session storage. Intake then displays the source card and applies accepted facts/artifacts with a source string like `card:<card-id>:intake:<mode>` instead of plain `intake:<mode>`.

The expected operator flow is:

1. Open a card.
2. Copy and run a command.
3. Paste output into that card's evidence box.
4. Click `Analyze pasted evidence`.
5. Review proposals in Intake.
6. Apply reviewed evidence from that source card.
7. Return to Path with newly unlocked cards tied to that evidence source.

This is intentionally different from generic Intake. Generic Intake remains available, but card-originated evidence should carry card provenance.

## Linux vs Windows path routing

The path must separate Linux and Windows local privilege work by evidence from the active target context. Linux-only cards should require Linux foothold or Linux OS evidence. Windows-only cards should require Windows foothold or Windows OS evidence. Cross-platform credential cards should remain credential/service gated, not OS-only.

The path renderer now filters applicable cards through OS metadata so a Windows host does not receive Linux-only local privilege cards and a Linux host does not receive Windows-only local privilege cards.

## Windows privilege-escalation source-mining pass

This pass adds a full Windows local privilege-escalation source-mining slice beside the Linux privilege cards. It converts the reusable public-safe value into contextual Windows Next Steps cards:

- `windows-identity-privilege-review`
- `windows-service-permission-review`
- `windows-unquoted-service-path-review`
- `windows-scheduled-task-chain-review`
- `windows-alwaysinstall-elevated-review`
- `windows-credential-trail-review`
- `windows-token-privilege-review`

Each Windows card is gated by `foothold.windows`, carries `os:['windows']`, explains command purpose, and produces specific facts such as `privesc.leads`, `service.abusable`, `task.abusable`, `installer.abusable`, `credential.candidate`, or `token.abusable`.
