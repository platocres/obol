# Obol v9.29 — Notes Impact, No-Flash Dashboard, and Queue Rebalance

Obol v9.29 changes Notes Integration from a coarse review counter into an explicit notes-to-product pipeline. The release keeps the 556-note disposition requirement, but treats it as an umbrella over themed review packets and visible product outcomes rather than as one giant anonymous queue item. It also closes the user-visible dashboard flash and establishes the runtime/test-retirement policy needed to start removing historical live layers safely.

## Notes-to-product impact

`data/product-hardening/notes-impact-current.js` is the stable current projection for Notes Integration impact. It derives its figures from the live public-safe review ledger and Field Notes rather than release-specific constants.

At the v9.29 baseline the source ledger remains:

```text
reviewed: 55
modeled: 43
private-reference-only: 12
superseded: 0
rejected: 0
pending-review: 501
total: 556
```

The dashboard and generated README summary now expose what those reviews produced: normalized Field Notes, tool-bound guidance, Path-bound guidance, Evidence/proof-boundary guidance, report/remediation guidance, mined themes, latest-wave impact, and open product gaps.

Bindings and code changes are deliberately counted separately. A Field Note appearing in curl context is not reported as a Tool Builder implementation change unless a reviewed source explicitly declares a `tool-builder-change` with proof references. The same separation applies to Path, Evidence parser, report generator, and workflow mechanics.

## Note output decision contract

`docs/NOTES-IMPACT.md` makes the disposition rubric explicit. Every modeled source must be assessed for durable outputs such as:

- Field Note
- Tool Builder Change
- Path Change
- Evidence Change
- Report Change
- troubleshooting/product-gap work where applicable

Beginning with v9.29 review waves, a modeled source must either declare its code-level product changes with proof references or include an explicit `guidanceOnlyReason`. Existing pre-v9.29 rows are not retroactively rewritten with invented metadata.

A modeled note cannot be considered fully acted on merely because educational prose was added when the source clearly exposes a missing tool option, Path branch, proof boundary, or reporting behavior.

## Packet-based burn-down

`notes-disposition-burn-down` remains the umbrella for all 556 staged notes. The queue now exposes themed child work for web upload/inclusion, XSS/session behavior, credentials/authentication, Windows privilege escalation, Linux privilege escalation, and Active Directory/pivoting.

This lets future agents and the dashboard show which subject matter was mined and what changed in Obol instead of reporting only a larger reviewed count.

## Queue authority cleanup

Current queue status is owned directly by `data/product-hardening/product-hardening-queue.js`. `data/product-hardening/work-packages.js` no longer reconstructs completed queue items or note progress from the current release number.

This removes a hidden release-layer dependency from Product Build Next and makes queue data itself the authoritative current state.

## Dashboard no-flash ownership

The user-visible dashboard flash is fixed in v9.29. `assets/app-v8.8.js` now intercepts `#/dashboard` before the historical `route()` renderer can paint, immediately installs a current Product Hardening loading shell, loads the current dashboard assets, and hands the same view to `renderProductHardeningDashboard()`.

This is a targeted current-route ownership change, not a claim that all historical dashboard assets have already been removed. Non-dashboard routes still use their existing runtime path until their own ownership areas are compacted.

## Runtime compaction and test retirement

`docs/RUNTIME-COMPACTION.md` now defines the explicit retirement lifecycle:

1. stable current owner;
2. observable equivalence;
3. real browser proof for user-visible route/runtime behavior where static assertions are insufficient;
4. migration safety where applicable;
5. current-owner or fixture regression protection;
6. removal or decoupling of remaining live dependencies on the historical owner;
7. historical asset removed from live startup;
8. obsolete implementation-shape assertions retired;
9. README/dashboard progress updated.

Development has a focused `node tools/scope-check.js` path. The complete preservation chain is owned by `node tools/run-historical-contracts.js`, and CI delegates the ready-PR/main/release-final historical gate to that named runner instead of duplicating a hand-maintained list in the workflow logic.

The v9.28 suite was narrowed where it had accidentally pinned mutable current README/release presentation. It now preserves the durable v9.28 wave-three note outputs and privacy/lineage boundaries without requiring v9.28 to remain the current product presentation forever.

## Browser proof before physical retirement

`tests/playwright-smoke.js` and `.github/workflows/browser-smoke.yml` provide the browser-level gate for Home, Targets, Evidence, Next Steps, Report, and Dashboard. The smoke run fails on browser/page errors and failed same-origin requests, verifies that Dashboard finishes with the current dashboard owner, and captures full-page screenshots as workflow artifacts.

This proof is deliberately separate from the fast Node scope check. Browser installation and screenshots belong in the dedicated CI job, while small data/docs/runtime edits can keep using focused deterministic checks locally.

Historical dashboard data cannot be removed merely because the current Dashboard renderer exists. Still-live historical cores retain initialization dependencies on some of that data. For example, `assets/core-v6.5.js` consumes `OBOL_DASHBOARD_V65`. Physical retirement therefore requires both green browser proof and dependency decoupling before those historical owners leave startup.

## What comes next

The no-flash route owner and retirement policy are complete. The next Product Build Next item is Playwright browser smoke coverage. Once that exact-head browser gate is green, the queue can mark browser proof complete and proceed to `runtime-dashboard-layer-retirement`, where the remaining historical dashboard dependencies must be mapped and decoupled before files leave live startup.

This ordering is intentional: **current owner -> real browser proof/equivalence -> dependency removal -> physical layer removal -> obsolete-test retirement**, not “delete old files and hope the static assertions were enough.”

## Compatibility and proof boundary

Workspace/runtime schema remains v8.8. v9.29 does not add a versioned app/core/project-model/style mini-runtime. Obol remains browser-local, copy-only, human-run, and Evidence-gated. Private raw source notes remain outside the public repository, and note-derived guidance cannot execute commands or become report-ready proof by itself.

## README handoff

README now points future agents to the notes-impact and runtime-compaction contracts, exposes the notes review funnel separately from guidance and code-level mechanics, and makes the focused scope-check versus named historical final gate explicit. Product Build Next remains generated from shared queue/package data rather than hand-maintained prose.

## Product-hardening queue

v9.29 closes `notes-impact-dashboard`, `runtime-dashboard-no-flash`, and `runtime-test-retirement-policy`. Playwright browser smoke is intentionally the next gate before physical dashboard-layer retirement, after which the themed Notes Integration packets remain visible under the 556-note umbrella.

## Release gate

The release-final head must pass smoke, preflight, the complete named historical contract runner, release-quality validation, generated README/Product Build Next synchronization, browser smoke where configured, and the v9.29 item-specific regression suite on the same exact commit before merge.

For local reproduction of the complete preservation gate, use `node tools/run-historical-contracts.js`; CI remains authoritative for merge readiness on the exact release-final head.
