# Obol v9.29 — Notes Impact, Dashboard Compaction, and Queue Rebalance

Obol v9.29 changes Notes Integration from a coarse review counter into an explicit notes-to-product pipeline. The release keeps the 556-note disposition requirement, but treats it as an umbrella over themed review packets and visible product outcomes rather than as one giant anonymous queue item. It also closes the user-visible Dashboard flash, proves the route in a real browser, and physically retires the historical Dashboard data/presentation owners that no longer belong in live startup.

## Notes-to-product impact

`data/product-hardening/notes-impact-current.js` is the stable current projection for Notes Integration impact. It derives its figures from the live public-safe review ledger and Field Notes rather than release-specific constants.

At the v9.29 baseline the source ledger remains:

```text
reviewed: 55
modeled: 43
private-reference-only: 12
superseded: 0
rejected: 0
pending-review: 501
total: 556
```

The dashboard and generated README summary now expose what those reviews produced: normalized Field Notes, tool-bound guidance, Path-bound guidance, Evidence/proof-boundary guidance, report/remediation guidance, mined themes, latest-wave impact, and open Notes Integration work. The Dashboard also lists the public outputs from the latest review wave so a reviewer can see what actually came out of that work instead of only seeing a larger reviewed count.

Bindings and code changes are deliberately counted separately. A Field Note appearing in curl context is not reported as a Tool Builder implementation change unless a reviewed source explicitly declares a `tool-builder-change` with proof references. The same separation applies to Path, Evidence parser, report generator, and workflow mechanics.

## Note output decision contract

`docs/NOTES-IMPACT.md` makes the disposition rubric explicit. Every modeled source must be assessed for durable outputs such as:

- Field Note
- Tool Builder Change
- Path Change
- Evidence Change
- Report Change
- troubleshooting/product-gap work where applicable

Beginning with v9.29 review waves, a modeled source must either declare its code-level product changes with proof references or include an explicit `guidanceOnlyReason`. Existing pre-v9.29 rows are not retroactively rewritten with invented metadata.

A modeled note cannot be considered fully acted on merely because educational prose was added when the source clearly exposes a missing tool option, Path branch, proof boundary, or reporting behavior.

## Packet-based burn-down

`notes-disposition-burn-down` remains the umbrella for all 556 staged notes. The queue now exposes themed child work for web upload/inclusion, XSS/session behavior, credentials/authentication, Windows privilege escalation, Linux privilege escalation, and Active Directory/pivoting.

This lets future agents and the dashboard show which subject matter was mined and what changed in Obol instead of reporting only a larger reviewed count.

## Queue authority cleanup

Current queue status is owned directly by `data/product-hardening/product-hardening-queue.js`. `data/product-hardening/work-packages.js` no longer reconstructs completed queue items or note progress from the current release number.

This removes a hidden release-layer dependency from Product Build Next and makes queue data itself the authoritative current state.

## Dashboard current ownership

The user-visible Dashboard flash is fixed in v9.29. `assets/runtime-current.js` claims Dashboard intent during startup and installs the current Product Hardening loading shell. `assets/dashboard-route-current.js` owns the current route render and repairs any delayed historical repaint attempt.

That current owner is now the live Dashboard presentation path. Historical Dashboard rendering code no longer needs to win a race, because the historical Dashboard-only presentation overlays proven unnecessary by browser/equivalence testing have left live startup.

## Runtime compaction and test retirement

`docs/RUNTIME-COMPACTION.md` defines the explicit retirement lifecycle:

1. stable current owner;
2. observable equivalence;
3. real browser proof for user-visible route/runtime behavior where static assertions are insufficient;
4. migration safety where applicable;
5. current-owner or fixture regression protection;
6. removal or decoupling of remaining live dependencies on the historical owner;
7. historical asset removed from live startup;
8. obsolete implementation-shape assertions retired;
9. README/dashboard progress updated.

Development has a focused `node tools/scope-check.js` path. The complete preservation chain is owned by `node tools/run-historical-contracts.js`, and CI delegates the ready-PR/main/release-final historical gate to that named runner instead of duplicating a hand-maintained list in workflow logic.

Historical suites were narrowed where they had accidentally pinned mutable current queue totals, README presentation, or superseded runtime ownership shapes. Those tests now protect durable milestones and current-owner/fixture contracts instead of requiring old delivery layers to remain live forever.

## Browser proof and completed Dashboard retirement

`tests/playwright-smoke.js` and `.github/workflows/browser-smoke.yml` provide the browser-level gate for Home, Targets, Evidence, Next Steps, Report, and Dashboard. The smoke run fails on browser/page errors and failed same-origin requests, records Dashboard paints through the historical timer window, verifies that no historical Dashboard owner appears before or after the current owner, and captures full-page screenshots as workflow artifacts.

That Chromium gate is green and `qa-playwright-smoke` is complete. The exact-head full historical contract chain, preflight, and lightweight smoke also passed before the retirement item was closed.

All sixteen versioned `data/dashboard-v*` owners are absent from live browser startup. Proven Dashboard-only v5.x/v6.x presentation overlays have likewise left startup while remaining represented in the frozen historical ledger where they are still useful as fixtures. `data/dashboard-compat-current.js` is the single stable data-only compatibility seam for historical metadata still consumed by surviving core overlays.

Node current-runtime execution uses the same compact seam rather than executing the sixteen historical Dashboard data owners. `tools/validate-dashboard-compat-equivalence.js` executes the old Dashboard data owners only as an isolated fixture projection and compares their normalized metadata against the compact seam. Operator-relevant v6.5 AD CS mutations remain owned by `data/source-delivery-v6.5.js`, so the compatibility seam does not become another hidden domain-behavior layer.

The Product Hardening Dashboard exposes the resulting runtime state directly through current/historical script counts, browser proof status, and an ownership-area retirement matrix covering Dashboard, Home/Path, Tool Builders, Evidence, Reports, and CSS.

## What comes next

With `runtime-dashboard-layer-retirement` complete, Product Build Next returns to Notes Integration rather than inventing another runtime-only release wave. The next recommended package is **Notes Impact and Themed Burn-down**, entered through the 556-note umbrella and executed through coherent themed packets.

For each modeled source, future work must answer what normalized guidance was produced, where it is bound, whether it required a code-level product mechanics change, and what product gaps remain. That keeps note mining tied directly to educational content, tool options, Path behavior, Evidence capture, reporting, troubleshooting, and explicit missing capability.

Runtime compaction remains an architectural program. Later work should apply the same proven method by ownership area to Home/Path, Tool Builders, Evidence, Reports, and CSS: **current owner -> real browser proof/equivalence -> dependency removal -> physical layer removal -> obsolete-test retirement**. Old layers should not remain live merely because they are old tests' easiest execution path.

## Compatibility and proof boundary

Workspace/runtime schema remains v8.8. v9.29 does not add a versioned app/core/project-model/style mini-runtime. Obol remains browser-local, copy-only, human-run, and Evidence-gated. Private raw source notes remain outside the public repository, and note-derived guidance cannot execute commands or become report-ready proof by itself.

## README handoff

README points future agents to the notes-impact and runtime-compaction contracts, exposes the notes review funnel separately from guidance and code-level mechanics, and makes the focused scope-check versus named historical final gate explicit. Product Build Next remains generated from shared queue/package data rather than hand-maintained prose.

## Product-hardening queue

v9.29 closes `notes-impact-dashboard`, `runtime-dashboard-no-flash`, `runtime-test-retirement-policy`, `qa-playwright-smoke`, and `runtime-dashboard-layer-retirement`. Architecture/runtime advances to 9/12 complete, and Product Build Next returns to the Notes Impact and Themed Burn-down package with the umbrella plus themed packets still visible.

## Release gate

The release-final head must pass smoke, preflight, the complete named historical contract runner, release-quality validation, generated README/Product Build Next synchronization, browser smoke, and the v9.29 item-specific regression suite on the same exact commit before merge.

For local reproduction of the complete preservation gate, use `node tools/run-historical-contracts.js`; CI remains authoritative for merge readiness on the exact release-final head.
