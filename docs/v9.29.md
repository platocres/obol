# Obol v9.29 — Notes Impact, Dashboard Compaction, and Queue Rebalance

Obol v9.29 changes Notes Integration from a coarse review counter into an explicit notes-to-product pipeline. The release keeps the 556-note disposition requirement, but treats it as an umbrella over themed review packets and visible product outcomes rather than as one giant anonymous queue item. It also closes the user-visible Dashboard flash, adds real browser proof, and physically retires the proven historical Dashboard runtime owners from live startup.

## Notes-to-product impact

`data/product-hardening/notes-impact-current.js` is the stable current projection for Notes Integration impact. It derives its figures from the live public-safe review ledger and Field Notes rather than release-specific constants.

At the v9.29 baseline the source ledger remains:

```text
reviewed: 55
modeled: 43
private-reference-only: 12
superseded: 0
rejected: 0
pending-review: 501
total: 556
```

The dashboard and generated README summary expose what those reviews produced: normalized Field Notes, tool-bound guidance, Path-bound guidance, Evidence/proof-boundary guidance, report/remediation guidance, mined themes, latest-wave impact, and open Notes Integration work. The Dashboard also lists the public outputs from the latest review wave so a reviewer can see what actually came out of that work instead of only seeing a larger reviewed count.

Bindings and code changes are deliberately counted separately. A Field Note appearing in curl context is not reported as a Tool Builder implementation change unless a reviewed source explicitly declares a `tool-builder-change` with proof references. The same separation applies to Path, Evidence parser, report generator, and workflow mechanics.

## Note output decision contract

`docs/NOTES-IMPACT.md` makes the disposition rubric explicit. Every modeled source must be assessed for durable outputs such as:

- Field Note
- Tool Builder Change
- Path Change
- Evidence Change
- Report Change
- troubleshooting/product-gap work where applicable

Beginning with v9.29 review waves, a modeled source must either declare its code-level product changes with proof references or include an explicit `guidanceOnlyReason`. Existing pre-v9.29 rows are not retroactively rewritten with invented metadata.

A modeled note cannot be considered fully acted on merely because educational prose was added when the source clearly exposes a missing tool option, Path branch, proof boundary, or reporting behavior.

## Packet-based burn-down

`notes-disposition-burn-down` remains the umbrella for all 556 staged notes. The queue exposes themed child work for web upload/inclusion, XSS/session behavior, credentials/authentication, Windows privilege escalation, Linux privilege escalation, and Active Directory/pivoting.

This lets future agents and the dashboard show which subject matter was mined and what changed in Obol instead of reporting only a larger reviewed count.

## Queue authority cleanup

Current queue status is owned directly by `data/product-hardening/product-hardening-queue.js`. `data/product-hardening/work-packages.js` no longer reconstructs completed queue items or note progress from the current release number.

This removes a hidden release-layer dependency from Product Build Next and makes queue data itself the authoritative current state.

## Dashboard no-flash ownership

The user-visible Dashboard flash is fixed in v9.29. `assets/runtime-current.js` claims Dashboard intent before the historical compatibility startup path can render a Dashboard, protects the shared view while that intent is active, and installs the current Product Hardening loading shell. `assets/dashboard-route-current.js` then owns the current route render and repairs any delayed historical repaint attempt.

Real Chromium paint-history proof confirms that no historical Dashboard owner appears before or after the current owner during the legacy timer window.

## Physical Dashboard runtime retirement

The proof-gated Dashboard compaction work is complete.

- All sixteen versioned `data/dashboard-v*` owners are absent from live browser startup while remaining explicitly represented in the frozen historical ledger for fixture/equivalence purposes.
- Fourteen proven Dashboard-only historical `app-v5.x`/`app-v6.x` presentation overlays have left live startup.
- `data/dashboard-compat-current.js` is the single data-only compatibility seam for Dashboard metadata still consumed by historical core overlays.
- Node current-runtime loading uses the same compact seam rather than executing the retired versioned Dashboard data owners.
- `tools/validate-dashboard-compat-equivalence.js` executes the old Dashboard data owners only as an isolated historical fixture and compares their normalized metadata with the current compatibility seam.
- Operator-relevant v6.5 AD CS mutations remain owned by `data/source-delivery-v6.5.js` rather than leaking back into Dashboard compatibility.
- `tools/audit-dashboard-runtime-dependencies.js --require-retired` reports zero live historical Dashboard data owners.

This closes `runtime-dashboard-layer-retirement` on evidence, not merely because files changed.

## Runtime compaction and test retirement

`docs/RUNTIME-COMPACTION.md` defines the explicit retirement lifecycle:

1. stable current owner;
2. observable equivalence;
3. real browser proof for user-visible route/runtime behavior where static assertions are insufficient;
4. migration safety where applicable;
5. current-owner or fixture regression protection;
6. removal or decoupling of remaining live dependencies on the historical owner;
7. historical asset removed from live startup;
8. obsolete implementation-shape assertions retired;
9. README/dashboard progress updated.

Development has a focused `node tools/scope-check.js` path. The complete preservation chain is owned by `node tools/run-historical-contracts.js`, and CI delegates the ready-PR/main/release-final historical gate to that named runner instead of duplicating a hand-maintained list in workflow logic.

Historical v9.x suites that had pinned mutable current queue totals were narrowed to protect their durable release milestones and behavior floors instead. That is the intended test-retirement model: preserve the contract, not obsolete delivery shape or a frozen copy of today’s queue.

## Browser proof

`tests/playwright-smoke.js` and `.github/workflows/browser-smoke.yml` provide the browser-level gate for Home, Targets, Evidence, Next Steps, Report, and Dashboard. The smoke run fails on browser/page errors and failed same-origin requests, records Dashboard paints through the historical timer window, verifies that no historical Dashboard owner appears before or after the current owner, and captures full-page screenshots as workflow artifacts.

The exact v9.29 head that established the physical retirement boundary passed this browser gate together with preflight, lightweight smoke, and the complete historical contract runner. The queue now records the retirement item as complete.

The Product Hardening Dashboard exposes runtime state through current/historical script counts, Dashboard retirement status, browser proof, and an ownership-area retirement matrix covering Dashboard, Home/Path, Tool Builders, Evidence, Reports, and CSS. The matrix shows where current ownership exists, what proof is present, and whether old implementation tests have actually been retired.

## What comes next

With Dashboard retirement proven, Product Build Next returns to **Notes Impact and Themed Burn-down**. The entry item is the 556-note disposition umbrella, but work should proceed through coherent themed packets rather than anonymous note-count waves.

Each packet must answer what the source material taught Obol, where normalized guidance is bound, whether Tool Builder/Path/Evidence/report/workflow mechanics changed, what proof backs those changes, and what product gaps remain open.

Runtime compaction remains a continuing architecture direction. Future ownership-area retirement for Home/Path, Tool Builders, Evidence, Reports, and CSS should use the same current-owner -> equivalence -> browser proof where needed -> dependency removal -> physical layer removal -> obsolete-test retirement sequence. Those areas should be advanced when they become the active queue context rather than obscuring the notes pipeline that is now highest priority.

The target remains a boring current app, not a permanent stack of historical UI owners.

## Compatibility and proof boundary

Workspace/runtime schema remains v8.8. v9.29 does not add a versioned app/core/project-model/style mini-runtime. Obol remains browser-local, copy-only, human-run, and Evidence-gated. Private raw source notes remain outside the public repository, and note-derived guidance cannot execute commands or become report-ready proof by itself.

## README handoff

README points future agents to the notes-impact and runtime-compaction contracts, exposes the notes review funnel separately from guidance and code-level mechanics, and makes the focused scope-check versus named historical final gate explicit. Product Build Next remains generated from shared queue/package data rather than hand-maintained prose.

## Product-hardening queue

v9.29 closes `notes-impact-dashboard`, `runtime-dashboard-no-flash`, `runtime-test-retirement-policy`, `qa-playwright-smoke`, and the proof-gated `runtime-dashboard-layer-retirement`. Product Build Next now returns to `notes-disposition-burn-down` and its themed Notes Integration packets.

## Release proof

The v9.29 implementation head passed preflight, lightweight smoke, the complete named historical contract runner, and real browser smoke on the same exact commit before the Dashboard retirement gate was recorded complete. The maintenance closure keeps that proven implementation unchanged and synchronizes the queue, regression expectation, release documentation, and generated README/dashboard handoff with the evidence already obtained.
