# Obol v9.29 — Notes Impact Dashboard and Queue Rebalance

Obol v9.29 changes Notes Integration from a coarse review counter into an explicit notes-to-product pipeline. The release keeps the 556-note disposition requirement, but treats it as an umbrella over themed review packets and visible product outcomes rather than as one giant anonymous queue item.

## Notes-to-product impact

`data/product-hardening/notes-impact-current.js` is the stable current projection for Notes Integration impact. It derives its figures from the live public-safe review ledger and Field Notes rather than release-specific constants.

At the v9.29 baseline the source ledger remains:

```text
reviewed: 55
modeled: 43
private-reference-only: 12
superseded: 0
rejected: 0
pending-review: 501
total: 556
```

The dashboard and generated README summary now expose what those reviews produced: normalized Field Notes, tool bindings, Path bindings, Evidence/proof-boundary guidance, report/remediation guidance, mined themes, latest-wave impact, and open product gaps.

## Note output decision contract

`docs/NOTES-IMPACT.md` makes the disposition rubric explicit. Every modeled source must be assessed for one or more durable outputs:

- Field Note
- Tool Builder Change
- Path Change
- Evidence Change
- Report Change
- troubleshooting/product-gap work where applicable

A modeled note cannot be considered fully acted on merely because educational prose was added when the source clearly exposes a missing tool option, Path branch, proof boundary, or reporting behavior.

## Packet-based burn-down

`notes-disposition-burn-down` remains the umbrella for all 556 staged notes. The queue now exposes themed child work for web upload/inclusion, XSS/session behavior, credentials/authentication, Windows privilege escalation, Linux privilege escalation, and Active Directory/pivoting.

This lets future agents and the dashboard show which subject matter was mined and what changed in Obol instead of reporting only a larger reviewed count.

## Queue authority cleanup

Current queue status is owned directly by `data/product-hardening/product-hardening-queue.js`. `data/product-hardening/work-packages.js` no longer reconstructs completed queue items or note progress from the current release number.

This removes a hidden release-layer dependency from Product Build Next and makes queue data itself the authoritative current state.

## Runtime compaction handoff

v9.29 explicitly promotes runtime-layer retirement into Product Build Next. The next recommended work package is Dashboard Runtime Compaction:

1. stop historical dashboard content from painting before the current dashboard;
2. retire historical dashboard owners from live startup after equivalence is proven;
3. codify the current-owner -> equivalence -> fixture -> live-layer removal -> obsolete-test retirement lifecycle for the remaining runtime areas.

`docs/RUNTIME-COMPACTION.md` defines that handoff. The goal is not to keep old layers and old implementation-shape tests forever; it is to preserve durable behavior until a current owner has proven equivalence, then remove obsolete execution paths and retire tests that no longer protect a real contract.

## Validation strategy

Development now has a focused `node tools/scope-check.js` path for the active work package. The complete historical chain remains the final/main preservation boundary through `tools/run-historical-contracts.js` and CI.

v9.29 adds `tools/validate-notes-impact.js` and `tests/run-v9.29-tests.js` to protect the notes-impact projection, Dashboard/README wiring, packetized queue model, next runtime-compaction handoff, and the prohibition on fake v9.29 runtime overlays.

Historical suites may be updated when they accidentally pin mutable current-product presentation instead of the durable behavior belonging to that historical release. The historical gate remains intact; stale assertions are narrowed rather than bypassed.

## Compatibility and proof boundary

Workspace/runtime schema remains v8.8. v9.29 does not add a versioned app/core/project-model/style mini-runtime. Obol remains browser-local, copy-only, human-run, and Evidence-gated. Private raw source notes remain outside the public repository, and note-derived guidance cannot execute commands or become report-ready proof by itself.

## Release gate

The release-final head must pass smoke, preflight, the complete named historical contract runner, release-quality validation, generated README/Product Build Next synchronization, and the v9.29 item-specific regression suite on the same exact commit before merge.

For local reproduction of the complete preservation gate, use `node tools/run-historical-contracts.js`; CI remains authoritative for merge readiness on the exact release-final head.
