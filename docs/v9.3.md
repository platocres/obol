# Obol v9.3 - asset integrity and coherent burn-down governance

v9.3 completes `cc-asset-validation`, the highest-priority live Product Build Next item after v9.2 completed the current-release authority. The completed Orange 2025.03 methodology/source queue remains closed and regression-protected.

## Asset graph validation

`tools/validate-asset-references.js` now treats Obol's HTML pages as entrypoints into a local asset graph instead of checking only double-quoted `src` and `href` values in two hard-coded files.

The validator now:

- discovers repository HTML entrypoints;
- parses quoted and unquoted `src`, `href`, `poster`, `data`, and `srcset` references;
- follows inline CSS and linked stylesheet `url(...)` and `@import` references;
- follows supported literal and simple constant-backed dynamic script/style loads, dynamic imports, and browser worker/service-worker registrations from reachable JavaScript;
- resolves HTML references relative to their entrypoint, CSS references relative to their stylesheet, and browser-created dynamic resources relative to the site root;
- ignores deliberate non-file references such as fragments, external URLs, and data/blob/mailto-style schemes;
- rejects references that escape the repository root;
- reports the owning file, reference kind, original reference, and resolved path when an asset is missing.

The validator remains dependency-free and exports its graph-validation helpers so the current regression suite can exercise realistic fixtures directly.

## Coherent Product Build Next work packages

v9.3 also changes the Product Hardening operating model so future agents are not trained to stop after one queue item.

`data/product-hardening/work-packages.js` is a stable companion to the atomic queue. It groups related items by ownership area, dependencies, related follow-on work, parallel-safety metadata, recommended batching, and package guidance. The highest-priority queued item remains the entry point, but the README and Product Hardening Dashboard now show the coherent package surrounding that item.

The intended execution model is:

- start at the highest-priority queued item;
- inspect its same-ownership work package;
- burn down as many live package items as can be implemented and fully tested without materially expanding architectural context or blast radius;
- keep one active release/product-hardening PR rather than opening one PR per item;
- preserve independent acceptance criteria, validation commands, proof files, status, and item-specific tests for every queue item advanced or closed;
- stop expanding the package when the next item is genuinely a different engineering problem.

This gives agents permission to make a meaningful engineering pass without turning the queue into a random grab bag or weakening the item-specific Definition of Done.

For v9.3, the asset-integrity implementation closes the entry item and strengthens its existing asset-reference QA foundation. The remaining queued Playwright browser-smoke item introduces browser installation and screenshot infrastructure rather than another asset-resolution rule, so it remains separate instead of expanding this release's dependency and CI blast radius.

## CI and release gate

`tools/release-smoke.js` now consumes the same full asset validator, so ordinary release-branch pushes fail immediately when a reachable local asset disappears. The existing duplicate index-script/stylesheet check remains intact.

While tracing the required release flow, v9.3 also corrected a stale preflight assumption. `tools/release-preflight.js` previously required `core-vX.Y.js` and `project-model-vX.Y.js` for every current release, contradicting the v9 no-fake-runtime-layer rule. Preflight is now phase-aware: historical runtime releases retain the old wiring check, while Product Hardening releases validate the stable current-release authority, product queue contracts, full asset graph, generated Product Build Next, open-PR uniqueness, and current release suite without demanding fake v9 runtime files.

`tools/validate-product-hardening-queue.js` also validates the work-package schema, requires package recommendations to begin with the highest-priority queued item, checks that README/BUILDING/Product Hardening guidance explicitly supports coherent multi-item burn-down, and verifies both dashboard entrypoints consume the package source.
