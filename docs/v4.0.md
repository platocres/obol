# Obol v4.0

Obol v4.0 is an execution-context release built from the explicit v3.9 README requirement that Path consider whether the operator is working from Kali or from a Windows host on a given step.

The execution model does not change. Obol remains static, browser-local, review-first, and human-run only. It does not run commands, install tools, authenticate to targets, create pivots, or validate access by itself.

## Why v4.0

By v3.9, Obol could rank methodology using evidence, information gain, reachability, pivot state, tool intent, and conservative outcome proof. One practical distinction was still missing from the decision layer: the same technique can have very different preferred implementations depending on where the operator is currently working.

Examples include Impacket or NetExec from Kali versus Rubeus or PowerView from a Windows foothold, BloodHound Python versus SharpHound, secretsdump versus mimikatz, and remote execution from Kali versus native Windows tooling.

v4.0 makes that execution side explicit without turning it into a prerequisite or pretending Obol knows where a command was run unless the operator records it.

## Per-context operator execution state

Each active host/domain context can store one planning mode:

- `either` — decide per step; no platform ranking preference
- `kali` — prefer Kali-side implementations when one is identified
- `windows` — prefer Windows-host implementations when one is identified

The choice is context-scoped. Switching to another host or domain does not silently carry a platform assumption into the new context.

The default is `either`, which preserves v3.9 behavior until the operator explicitly chooses a side.

## Command execution-side classification

v4.0 adds a reusable command-side classification contract:

- `kali`
- `windows`
- `target`
- `either`

Explicit future command metadata (`operatorSurface40`) wins over inference.

The first inference pass recognizes strongly associated project tool families and command shapes, including Kali-side NetExec/Impacket/Certipy/BloodHound Python/Evil-WinRM/xfreerdp, Windows-side Rubeus/mimikatz/SharpHound/PowerView/PowerShell/native AD tooling, target-local shell techniques, and neutral commands where one side cannot be identified safely.

Target-local and neutral commands do not receive a platform mismatch penalty.

## Path ranking behavior

Operator platform is deliberately a small ranking signal, not a methodology gate.

When an explicit mode is selected:

- a card with a matching side receives a small positive signal
- a card with target-local or neutral execution remains neutral
- a card with only an identified opposite-side implementation receives a small negative signal
- the technique remains applicable and visible

Evidence, prerequisites, information gain, reachability, prior activity, and other existing ranking inputs continue to own methodology applicability.

## Next Steps UI

Next Steps now includes a context-scoped **Working from** selector with Either, Kali, and Windows host choices.

Recommendations can show the execution-context reason and the number of Kali-side, Windows-side, and target-local implementations identified on the card.

Changing the selector recalculates the current Path presentation immediately without mutating evidence or activity history.

## Methodology-card guidance

Expanded methodology cards now show the current operator execution context, implementation counts by side, an execution-side badge on each command block, and a highlight on commands and variants compatible with the selected side.

Non-matching commands remain visible. v4.0 is guidance, not a filter that hides fallbacks.

## Activity provenance

Newly recorded activity snapshots two additional fields:

- the planning mode selected when the activity was recorded
- the execution side inferred from the historical command snapshot

This keeps later changes to the operator-mode selector from rewriting historical context.

Existing activities are not backfilled with guessed execution-side provenance.

## Report integration

Generated reports gain an **Operator Execution Context** section when v4.0 activity provenance exists.

The section lists recent activity with timestamp, engagement context, activity, recorded planning side, and inferred command side.

The section is provenance only. It explicitly does not prove that a command ran successfully.

## Information architecture

v4.0 adds no primary navigation destination.

Ownership remains with Next Steps for execution-aware recommendation ordering, Methodology for implementation choices, Evidence for review-first state mutation, Targets for target inventory and Nmap discovery, and Report for historical proof/report consumption.
