# Obol v3.8

v3.8 advances the pivot-state, compromise-path, proof-readiness, and full-session regression priorities carried forward from the v3.7 README.

The release keeps Obol's human-run model and small v3 information architecture. It deepens existing workflow owners instead of adding another primary destination.

## Pivot operational state

v3.7 made path verification freshness affect recommendation confidence. v3.8 adds the operational state needed to explain *why* a path is or is not trustworthy.

Explicit network paths can now retain:

- source interface identity
- listener health: unknown, healthy, degraded, or down
- listener / route check note
- last health-check time
- bounded operational history

Operational checks are append-only history entries. Obol does not silently change a path from active to broken merely because listener health is recorded as down. Lifecycle state and operational health remain separate operator-controlled concepts.

## Reachability confidence uses listener health

Target-specific reachability from v3.7 remains the base model, but pivot-backed recommendation confidence is now adjusted by operational state.

- recently verified healthy pivots retain the strongest boost
- unknown listener health slightly reduces confidence
- degraded listener health reduces the boost substantially
- a listener recorded down removes the positive pivot-reachability boost
- stale or unverified paths continue to receive no positive service-reachability boost

The path itself remains recorded. v3.8 changes recommendation confidence, not historical evidence.

## Pivot operations journal

The Reachability workspace now exposes per-path operational controls and recent history.

Operators can record the source interface, listener health, and a route/listener note as one operational check. The check refreshes explicit verification time and appends a history record containing the state at that moment.

This provides a lightweight troubleshooting ledger for repeated lab pivots without introducing a separate pivot-management page.

## Transition-aware compromise paths

v3.7 added multi-hop artifact chains derived from conservative producer/consumer lineage. v3.8 annotates those chains when one exact historical activity can be identified for a hop.

When producer and consumer lineage point to one exact activity, the chain can show the recorded transition, such as credential, foothold, privilege, network, or objective. If the hop cannot be tied to one exact activity, it remains labeled as a methodology link instead of guessing.

This keeps compromise-path summaries useful while preserving the project's evidence-first uncertainty model.

## Transition-specific proof templates

The v3.5 Report proof model remains the owner of readiness. v3.8 extends its automatic requirements for material transitions.

- foothold transitions require a recorded foothold/shell outcome fact
- privilege transitions require a recorded `access.*` outcome fact
- objective transitions require a recorded `objective.*` outcome fact
- network transitions require an active path that is also operationally verified

These checks use existing ledger state. Manual external-proof confirmations remain manual, and Obol still does not inspect screenshot contents.

## Full-session regression expansion

The v3.8 regression suite adds another mixed Active Directory transcript fixture containing anonymous LDAP enumeration followed by Rubeus ticket import. The regression verifies that the two commands remain separate methodology activities and that only the ticket-import activity establishes Kerberos ticket state.
